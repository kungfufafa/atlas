## Checked invariants

- **Trust and scope:** The producer gets only `stageBytes`; identity/finalize/retry/read/revoke remain with trusted server code. Returned tool metadata is never parsed as a publication record. Publication identity includes org/profile/session/actor/run/execution/call, and the fingerprint binds those fields plus the complete ordered output set. Reads resolve org/profile/session-bound, nonrevoked DB records. Mandatory host authorization is separate from database scope/liveness validation. The foundation does not invent a currently implemented fenced run lease.
- **Exact bytes and private identifiers:** Producer bytes are copied synchronously before any await and staged into exclusive random objects. The stored snapshot ID does not appear in the public record. Read checks regular file, single link, size, final-component no-follow and SHA-256 against the DB record. Mutable workspace paths are not reread for this byte-producing path. These checks support exact captured-byte delivery under the stated trusted-store assumptions; they do not prove source authorship or hostile-host immutability.
- **Atomicity and idempotency:** SQLite commits the execution fingerprint and all records in one IMMEDIATE transaction. Uniqueness failures roll back the execution reservation and every inserted output. Empty successful output sets are reserved too. Memory uses a synchronous validation/commit section and clones returned records. Exact retries can create different staged object/record IDs but resolve the original committed IDs, timestamps, bytes and revocation state. Conflicting identity, bytes, metadata, omitted/extra outputs or output ordinals cannot replace the committed set.
- **Failure semantics:** `finalize` requires actual protected-executor `success === true` and the canonical shared failed-data predicate. A failed/aborted result discards staging, without touching user output files. A valid input whose storage fails resolves `stageBytes`, poisons publication finalization, and cannot produce a partial committed set. Invalid/conflicting inputs reject and also poison the set. Uncertain DB commit errors retain snapshots; retry invokes persistence only, never the producer. Stage errors remain unrepairable by a DB-only retry, which is stated correctly.
- **Concurrency:** Closing before finalization prevents later staging; in-flight finalization and retries share one promise. Promise results are collected with `allSettled`; storage/validation failure prevents partial commit. Duplicate controllers stage distinct random objects, and the database fingerprint resolves the authoritative set. Current cleanup only concerns that controller's discarded/duplicate staging. It is not a generic garbage collector safe to call on an arbitrary object that another active publisher may soon reference.
- **Lifecycle and revocation:** Reads reauthorize after byte loading and reread the current nonrevoked record. Revoked publications remain referenced, preserving retention. SQLite FK cascades and memory scope cleanup remove authority on session/profile deletion, so recreating the same session ID does not revive old publications. Exact commit retry after revocation can return the original revoked metadata; this is idempotence, not renewed delivery authority. Future delivery must resolve the authorized current record before serving bytes.

## Conditions for later integration, already acknowledged in implementation notes

1. Only trusted server code may choose identity, pass a complete actual admitted-root inventory, and hold `finalize`. A TypeScript interface alone does not authenticate a caller. Tool JSON or tenant-authored custom code must never obtain the finalizer or raw DB/storage authority.
2. The authorizer and subsequent DB operations are not an atomic membership transaction. Cancellation/revocation may happen after the final check. Existing channel/session/principal checks must remain at delivery; do not advertise universal race-free authorization.
3. Private storage protection depends on real OS confinement and complete root inventory. The current tests do not run Bash/Python/custom-tool denial against the object store. Unrestricted host/admin/server code and the unsafe custom-tool opt-in remain outside that guarantee. Capturing selected existing files still requires its own beneath-root/parent-race-safe implementation.
4. Staging or uncertain-commit failures can retain unreferenced objects. There is no pending manifest for cold retry, retention scheduler, export/import mapping or crash-safe generic GC. `removeUnreferenced` performs check then unlink; a future collector must additionally coordinate with active staging and potential new references, rather than treating this method as an atomic no-future-reference proof.
5. Native byte producers, Bash/Python/custom output selection, actual executor completion wiring, all history/UI/channel/share readers and legacy republishing remain prerequisites for the race fix. The original counterexample must be rerun through actual publication-backed HTTP/channel reads after that cutover. This foundation alone supports no Atlas/Hermes quality or parity claim.

These are scope boundaries and future gates, not undisclosed claims of completed work. Within those boundaries, the implementation is consistent with the reviewed design and is suitable to carry forward as the foundation component.
