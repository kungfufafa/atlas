# Exact-byte publication foundation (unwired)

This patch adds a server-owned publication boundary; it does not fix the existing artifact attribution race until producers, compute selection and all consumers migrate together. No existing tool, `ToolContext`, protected executor, subscription runtime, HTTP route, artifact chip, channel worker, share service or history extractor invokes this foundation.

The producer contract lives in `packages/core/src/artifact-publication.ts`. `stageBytes({bytes, sourcePath, outputOrdinal})` accepts complete bytes and a canonical visible `artifacts/` locator, with at most 32 distinct output ordinals and 25 MiB per output. It copies bytes before yielding. Storage failures resolve normally while retaining a publication failure for finalization; they do not recategorize a successful workspace write. Invalid path/ordinal/size, conflicting ordinal, cancellation, or closed execution rejects. A caller that has already created an output must preserve its effect receipt even in those cases. Repeating the same ordinal/path/bytes is idempotent. Core wrappers can assign ordinals per invocation to avoid nested helpers choosing zero independently. The identity and storage ID cannot be supplied through this producer capability.

`ArtifactPublicationService.beginExecution(identity, admittedToolRoots, signal?)` returns `{producer, finalize, retryPublication}` to trusted server code. Only `producer` may later enter a tool context. The actual protected-executor envelope must reach `finalize`; both its `success === true` and `!isFailedToolResult(data)` are required. Failed/aborted operations discard staging and never create publication authority, including an outer success carrying `data.ok:false`, `data.success:false`, `data.isError:true`, or `data.error`. Nothing in returned tool JSON creates or reassigns a publication. The server caller retains the original result and user files regardless of publication status. A later history-distillation failure cannot change the already committed DB record; future consumers must resolve that record rather than infer authority from copied history fields.

The existing SQLite database gains execution and publication tables. One IMMEDIATE transaction commits the full output set, including an empty successful set. A canonical fingerprint binds exact org/profile/session/actor/run/execution/tool-call identity plus each ordinal/path/name/MIME/size/digest/evidence class. An exact retry returns the original IDs, timestamps and snapshots. Different bytes, metadata, identities or output sets conflict. A uniqueness error rolls back every row and the execution reservation. In-memory behavior uses the same fingerprint and synchronous commit section, clones externally returned records, and drops publication authority when sessions or profiles are deleted. SQLite uses its existing FK and connection/durability settings; no broader durability configuration changes are introduced.

The store writes opaque, exclusive private objects under `<configDirectory>/artifact-publications`, outside every caller-declared admitted tool filesystem root. Files and the containing directory are synced. Committed reads resolve a scoped DB record, read a bounded regular single-link object without following its final symlink, and verify exact size and SHA-256. Byte-producing tools avoid any later mutable workspace-path reread. Returned metadata omits the private snapshot ID/path. A forged path, receipt, sidecar or guessed publication ID has no authority. Failed/duplicate staging cleanup removes only objects with no DB reference and never touches the user workspace. Revoked publications stop reads and remain referenced for retention.

The mandatory authorization callback must implement current principal policy, independently of the model and tool output. The service additionally checks live org/profile/session consistency; DB writes and reads repeat that scope check, including organization archival and profile import status. Reads check authorization both before reading bytes and afterward and re-resolve the nonrevoked record. These callbacks and DB operations are not one atomic membership/ownership transaction: revocation can occur after the last check. No universal race-free authorization or fenced invocation lease is claimed. Existing org/channel/member authorization must remain in future consumers, and the separate restart-ownership audit provides no currently implemented lease primitive to assume here.

`retryPublication()` retries only a previously eligible failed commit using its frozen staged bytes. It never calls the producer. If the DB committed and then returned an error, the retained objects and canonical retry recover the original receipt. Uncertain failures retain staging instead of deleting a possibly referenced object. Stage validation/storage failures cannot be repaired by retrying DB persistence alone. A process crash before commit leaves unreferenced private objects; no durable pending-manifest resume or retention/GC scheduler is included. A future cleanup job must establish that an object is unreferenced and account for active staging before removal; no arbitrary age-based cleanup is activated here. Reopening SQLite verifies durable committed records and bytes, not a power-loss or distributed-filesystem fault model.

“Write-once” describes this storage API. Filesystem protection against default Bash/Python/custom tools depends on actual OS confinement, supported launchers, trusted root configuration and a complete admitted-root inventory at integration time. This patch checks supplied root separation but does not launch those tools or certify their policies. Unrestricted host/admin code, a server compromise, or `ATLAS_ALLOW_UNSANDBOXED_CUSTOM_TOOLS=1` remains outside that protection; such code can often rewrite files and the DB. A deliberate host write is tested to demonstrate digest rejection, not to claim host-proof immutability. There is no stronger separate-UID/object-store authority in this patch.

Selected-existing-file capture, parent-directory race protection for that capture, all producer hooks, preservation of ordinary Bash/Python delivery, ToolContext/executor wiring, UI and worker migration, legacy re-publication, publication-backed sharing, export/import and retention remain explicit follow-up work. The current evidence covers exact-byte foundation behavior only. It supplies no live model result, task-quality improvement, visual-quality guarantee or Atlas/Hermes parity claim.
