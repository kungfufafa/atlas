# Reviewed assembly plus selected-file publication

This scratch starts from reviewed consumer V2, applies only the exact three-path producer V2 delta, and adds the three reviewed selected-capture files. The pure assembly baseline is `36fa79f8a034e8e1fbcbbefe60b15ac6c7c4d516bd14043727a591cf88b86522` (2101files). The prospective design was written before source integration edits. Every reviewed input and root C5 remains unchanged; no AgentService, UI, route, platform worker or production activation was added by this component.

The server-owned `ArtifactPublicationExecution.stageSelectedFile({sourcePath, outputOrdinal})` shares the execution's complete output set with generated byte outputs. Only the trusted execution object exposes it. The existing `producer.stageBytes` and ToolContext publisher remain byte-only, fixed to tool_output_bytes and without owner/evidence/root/finalization selectors.

The service freezes the identity and configured profile root, validates the1024-character publication limit and selected-file eligibility before capture, checks current publication access before and after capture, checks private-store disjointness including that profile root, and supplies the current execution signal to both root anchoring and every actual capture. It uses the existing static descriptor-based capture worker and stores its returned exact bytes in the private immutable-through-API store. No private snapshot lookup falls back to rereading the workspace file. This component supports the configured profile root, not arbitrary per-tool cwd or model-selected roots.

Public records now distinguish tool_output_bytes from selected_workspace_capture. The latter's full validated metadata lives only in DB-private captureEvidence and is stripped from commit, list and read projections. The validator bounds numeric metadata, requires exact schema keys and reader/version/stability facts, and matches path, byte count and digest to the publication record. Selected-record fingerprints append the canonical capture evidence; generated-record fingerprints keep their previous exact representation and reject capture metadata. DB schema tables and storage APIs are unchanged because records already use JSON payloads.

An ordinal is reserved before invoking capture or authorization callbacks. This ordering includes reentrant trusted callbacks, not only ordinary asynchronous calls. Exact repeated path/ordinal selection within one execution reuses the pending or captured result, even if the workspace file later disappears. A different path/evidence class on that ordinal poisons the whole set. Receipt-persistence retry keeps the original captured snapshot and never recaptures. A new explicit controller under the same execution identity can deduplicate identical evidence or conflict after metadata/byte changes; that is distinct from automatic persistence retry.

Input/conflict/closed-state errors reject; asynchronous capture/storage failures are retained for the trusted finalizer. All failure paths retain user files and never re-execute an earlier producer. Pending capture participates in the same finalization wait and all-or-nothing DB commit as generated outputs. Actual failed protected results, including success:true with data.ok:false, remain ineligible. Current revocation or cancellation prevents usable publication; the existing asynchronous authorization/commit windows are not made globally atomic.

## Limits and activation gates

This is a server-owned selected-file publication API, not a model-exposed publish tool, automatic Bash/Python capture, UI/file delivery cutover or activated production harness. SourceEvidence states how bytes entered publication; selected capture does not prove which session authored the editable file. Stable observed metadata is not an atomic filesystem snapshot. Detailed inode/root metadata is private but not a cryptographic attestation against a hostile host.

Actual grant admission still needs the separate runtime work: arbitrary host skill code, local MCP, unsafe custom-JS modes, complete dynamic roots, shared-host transition and per-turn invoker/effect-user identity must be handled before strict activation. A staging disjointness check cannot prevent an already-admitted unsafe process from reading older blobs. This service's generated owner identity still requires a trusted caller and current mandatory authorizer; no provider call ID, tool JSON or run label establishes lease ownership. New actor/admission components must be explicitly merged and reviewed, not silently assumed present.

Existing store cleanup/uncertain-commit retention and non-atomic callback revocation limits remain. No universal host isolation, full race fix, lease/restart guarantee, provider generalization or Atlas/Hermes parity/live-gain claim follows from these owner gates.
