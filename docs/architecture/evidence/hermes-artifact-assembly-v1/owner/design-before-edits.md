# Prospective selected-file publication integration

Written before integration source edits. Pure assembly uses reviewed consumer V2, the exact three-path producer V2 delta, and the three selected-capture foundation files. Production C5 and every input remain immutable. Assembly is not activation.

The generated-byte producer remains byte-only and fixed to tool_output_bytes. A new server-only `ArtifactPublicationExecution.stageSelectedFile({sourcePath, outputOrdinal})` will stage explicit existing-file selections into the same complete output set. It is not exposed through ToolContext, tool-returned JSON, the model publisher, or an HTTP route. The trusted service binds owner identity before awaits and derives the configured profile root from that scope; no caller-supplied private/root path or owner fields enter selection. Current authorization and private-store disjointness against the actual profile root are checked before capture. The captured path must pass the stricter1024-character publication rule and the selected-capture eligibility rule before worker execution; every capture receives the execution's current signal. Production's broader runtime admission remains blocked separately.

Selection reserves an ordinal/promise synchronously before any await. Finalization awaits all reserved outputs, including mixed generated/captured sets. Capture/validation/authorization/cancellation failure poisons the whole set while retaining original workspace files and producer receipts. Exact repeated selection of the same path/ordinal within one execution reuses the retained capture rather than reading again. A conflicting method/path/ordinal poisons the set. Retrying failed receipt persistence uses retained snapshots only; it never recaptures automatically. A new explicit selection attempt under the same execution identity may conflict if bytes or capture metadata have changed.

Public records gain sourceEvidence=selected_workspace_capture. Full validated capture metadata is stored privately on the DB record and stripped from public projections. Its canonical fingerprint includes the existing reader/version, observed stable metadata, path, byte digest/size, root identity and regular-file identity/timestamps. The DB validates this shape, checks digest/size/path agreement with the publication, and includes it in selected-record commit fingerprints. Generated records reject capture metadata and retain their existing fingerprint representation byte-for-byte. No new table is needed because records already persist JSON payloads. Observed metadata stability is not an atomic filesystem snapshot or authorship proof.

Tests will cover mixed atomic sets, pending selected capture at finalize, evidence-class conflicts, exact retries without recapture, changed metadata under the same identity, forged tool metadata, digest/size mismatch, private metadata removal, wrong scope/current revocation, pre-capture strict path limits, cancellation, immutable delivery after workspace overwrite, and unchanged generated fingerprint/read behavior. Use real capture for bounded files and real SQLite plus in-memory DB where behavior differs; narrow deterministic barriers may exercise authorization/commit timing. Keep failed initial attempts, bounded gate logs and owner-versus-independent review counts separate. No paid calls, UI/AgentService activation, broad suite or runtime-confinement claim.
