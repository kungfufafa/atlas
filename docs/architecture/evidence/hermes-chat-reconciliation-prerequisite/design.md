# Chat interruption reconciliation: ownership prerequisite

No product patch is proposed for application. Candidate 5 has useful run-row CAS operations, but its chat approval lifecycle does not carry an ownership token through every write or maintain its lease. The four bounded counterexamples below show that appending a recovery scan to these primitives would be unsafe. This is the task's prerequisite path, not a claim that restart recovery is implemented.

## Bounded behavioral evidence

The source tree was copied from the exact C5 source archive into a new scratch and all 2,078 enumerated files verified. No source file was changed. Real SQLite connections provide the read/write barriers; the probes wrap selected adapter methods solely to control a deterministic interleaving and then call the original implementation. No model/provider calls occur.

1. **Live owner expiry and admitted approval.** Three real chat service fixtures remained in the same live process/registry through their real 30-second lease expiry (no clock mocks). Chat leases did not renew. One approval decision was held just before its approval-record upsert, after reading the pending approval and creating the grant. A second SQLite connection performed a hypothetical exact-owner + expired-lease CAS to cancelled and wrote expired approval/uncertain step. Releasing the original decision changed the run back to running, approval to approved, and step to running; its waiting invocation received a grant. No second external effect was executed. This demonstrates why a CAS-only reconciler would not fence that original writer; it does not claim current Atlas runs that reconciler.
2. **Shared checkpoint late writer.** `saveCheckpoint` read a live row and waited before its actual upsert. Another connection terminalized the expired run through owner CAS. Releasing the old upsert restored the prior awaiting-approval status, old owner and expired lease with its new checkpoint. This is a shared API counterexample; the inspected production caller is subagent snapshot persistence.
3. **Receipt preservation late writer.** A genuine `executeProtectedTool` result existed for one disposable counter effect. Old `ChatToolApprovalService.complete(..., [])` read the still-running step and waited before writing its no-receipt fallback. Another connection terminalized the run and persisted that genuine result as succeeded. Releasing old cleanup overwrote it with failed / `UNCONFIRMED_RESULT`. Counter remained one. The receipt insertion was deliberately performed by the fixture through the real adapter, not claimed to be an existing second background receipt worker.
4. **Crash between recovery writes.** A complete main/WAL/SHM copy of the prior actual after-effect SIGKILL database was used. A new child performed the hypothetical expired-owner run CAS, signalled the boundary, and was SIGKILLed before any step/approval update. A new process reopened cancelled run + running step + null receipt. Repeating an active-only CAS returned false. A recovery plan that considers the terminal run fully recovered would leave the unresolved step behind. The original DB file set was not opened or mutated.

A first setup attempt for case 4 copied only the SQLite main file and therefore did not contain the WAL-resident run. That attempt exited before a recovery action; its source reference and stderr are preserved under `recovery-crash/`. The corrected `recovery-crash-v2/` copies and hash-verifies all three closed SQLite files. The failure is not omitted and is not a product recovery result.

The original actual approval/before-effect/after-effect SIGKILL evidence remains at `/private/tmp/atlas-restart-reproduction`. These new tests supplement it with ownership and crash-atomicity counterexamples; they do not make that prior evidence into a test of a fixed implementation.

## Smallest safe implementation boundary

Implement a versioned **chat execution ownership protocol** first, across admission, live waits, dispatch, receipts and reconciliation. A scan/cleanup method alone is insufficient. Keep this bounded to owned chat executions; do not silently change automation/subagent behavior through legacy shared upserts.

Required server-side contract:

- Retain a non-model-controlled handle `{orgId, sessionId, principalUserId, runId, ownerToken, protocolVersion}` at turn admission. The owner token can reuse the existing random per-claim lease owner if every write validates it and tokens are never reused. Acquire once, retain it in the live invocation, and forward it into approval/dispatch/finish operations. An existing row matching only actor/session is not an ownership claim.
- Renew the lease during model waits, approval waits and tool execution. A renewal failure cancels further dispatch and rejects pending decisions. Timer presence alone is not proof: renewal must atomically verify owner/status and failures must be surfaced. A process paused beyond expiry must reacquire through the declared protocol or stop; it may not resume writing with its stale handle.
- Require the exact handle at every chat run/step/approval mutation. Perform the owner/status/tenant predicate and all related changes in one DB transaction. An independent `get()` followed by current unconditional upserts is not fencing. The in-memory adapter must implement the same semantic predicates. Existing raw upserts must not remain reachable for protocol-owned chat rows.
- Preserve genuine receipts independently from recovery diagnostics. Existing `resultJson` mixes a tool's real result with a generated `UNCONFIRMED_RESULT`; do not identify trustworthy receipts by scanning arbitrary tool JSON for an error code. Use explicit server-owned receipt provenance (a separate immutable receipt row or dedicated fields) and an exact run/call/action identity. Repeated receipt writes must be byte-identical/idempotent; a fallback cannot replace an existing receipt.
- Check ownership immediately before each tool dispatch and before granting an execution capability. A DB lease can fence future DB writes and dispatch admission; it cannot make an already running arbitrary external tool stop atomically. Recovered runs therefore remain uncertain about in-flight effects and do not automatically replay them. Cooperating idempotency/effect lookup is a later, explicit tool contract.
- Define a separate append-only path for late evidence from a previously admitted invocation. Rejecting its stale state writes must not silently discard an already completed effect's receipt. Bind this evidence to the original immutable invocation/call, retain it as late/unreconciled evidence without reopening the run or authorizing another effect, and require an explicit reconciliation rule before changing the outcome. This is distinct from accepting arbitrary stale overwrites.
- Fence transcript checkpoints or append preserved receipt evidence through a separately owned path. Otherwise rejecting a stale execution-step writer while allowing its old whole-history replacement does not establish a safe session continuation. This requirement is separate from the current in-process history-generation guard.

Suggested narrow DB commands (signatures are design, not implemented APIs):

```ts
pauseOwnedChatForApproval(handle, exactCall, approvalId, checkpoint)
decideOwnedChatApproval(handle, approvalId, canonicalActor, decision)
recordOwnedChatReceipt(handle, exactCall, receipt)
finishOwnedChat(handle, outcome, preservedReceipts)
reconcileExpiredOwnedChat({ orgId, sessionId, runId, expectedOwner, protocolVersion })
```

Each command needs explicit expected states and one transaction. For example, `reconcileExpiredOwnedChat` must atomically verify scope/version/owner/expired lease, expire pending approvals, retain immutable receipts, mark only unresolved effects uncertain, and terminalize the run with a durable interruption reason. Repeat invocation must return the same already-reconciled state, and a crash must yield either all old state or all reconciled state. No new grant is produced. A late writer with the old handle fails its guarded command and cannot restore active status or overwrite receipts. A currently renewed lease is excluded; a foreign tenant/session is excluded even if a run ID is known.

A `decideOwnedChatApproval` transaction should commit the approved record before exposing a grant to the invocation. If a process dies between approval persistence and returning the grant, the result remains an interrupted approval without execution. An owner check is still required at dispatch. Grant creation before durable approval plus an unconditional later write is not retained.

Legacy rows and deployment need an explicit rule. Current chat rows did not maintain heartbeats or guarantee writer fencing, so expiry cannot retroactively certify their owner is safely fenced. Do not auto-clean them under the new protocol while an old server could still write. Preserve their evidence and 409 refusal; use a controlled quiescent migration or an exclusive server-epoch mechanism before converting them. A PID string/port probe alone is not a robust host-independent ownership proof. Rolling versions that can still execute legacy unconditional SQL need a deployment boundary or database-enforced compatibility guard.

## Acceptance gates before enabling reconciliation

- Run the original three actual-kill boundaries against the new protocol. Counter 0/0/1 remains 0/0/1; old approval IDs remain 409; newly authorized actions are distinct.
- A live renewed owner cannot be reconciled. An expired old owner cannot pause, decide, write a checkpoint, dispatch a new mutation or overwrite receipts after fencing. Test both connections and an actual suspended/resumed child.
- Genuine saved receipts survive expiry and reconciliation; no receipt can be manufactured from a stored approval. Native receipt/history ordering remains tested separately.
- SIGKILL during the reconciliation transaction and immediately after commit yields all-old or all-new state. Repeating reconciliation is idempotent, including after the successful commit was not acknowledged.
- Tests cover wrong org/session/owner, current terminal rows, unknown legacy ownership, heartbeat failure, an in-flight tool that ignores cancellation, and late genuine results. These effects stay explicitly uncertain unless a declared reconciliation mechanism proves otherwise.
- Web and channel flows surface interruption/verification needs while retaining existing ACLs and 409 semantics. UI verification is required if those surfaces change.

These are unfulfilled implementation gates. No readiness/claim of a recovery fix or full cold native resume is made. A broader owner/receipt protocol is the concrete prerequisite established by this investigation.
