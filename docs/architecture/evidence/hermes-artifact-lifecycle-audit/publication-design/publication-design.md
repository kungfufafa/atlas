# Artifact publication boundary — design only

Recommendation: add a server-owned **session publication** record for exact deliverable bytes, distinct from a **workspace observation**. Adapt all automatic delivery consumers together; retain file discovery for tool feedback and profile browsing. Do not infer creation ownership from either record. This is a separate prospective change after candidate4, with no production patch or model/test run in this follow-up.

The confirmed barrier reproduction is in `run-CidGS4/evidence.json`. The design addresses that source attribution defect; it cannot certify that a selected file satisfies the task, was authored by this session, or contains correct information.

## Minimal record and capture contract

Use an additive `ArtifactPublication` record keyed by an opaque server ID: org/profile/session, canonical actor, run/execution/tool-call ID where applicable, intent kind, display/source relative path, filename, MIME, byte count, SHA-256, immutable snapshot ID, created time and revocation/lifecycle state. `sourceEvidence` distinguishes `tool_output_bytes`, `selected_workspace_snapshot`, and `legacy_republished_now`. It must not say “created by session” for the latter two. No model receives storage paths or authority to choose record ownership.

For tools already holding output bytes, create the publication from those exact bytes in the successful tool operation, paired with its actual versioned destination. Do not reread the path after another writer could replace it. A source path remains a human-readable/editable workspace locator, while the publication identifies one immutable byte sequence. A hash of a file observed earlier, followed by a later path read, is not equivalent.

For an explicitly selected existing file, use a single bounded capture of a regular file beneath the canonical allowed profile artifact root, then hash/store the captured bytes and serve that snapshot. Capture must reject escapes, metadata/working-source paths, nonregular files and oversized reads; detect/reject concurrent mutation when consistency cannot be established. `loadFileAsset` (`packages/core/src/files/assets.ts:29–88`) supplies useful bounded handle-read/O_NOFOLLOW patterns, but final-component O_NOFOLLOW plus preflight realpath is not a proof against mutable parent-directory races. The implementation gate must cover anchored beneath-root opening or an OS-confined capture reader for supported hosts. Pre/post-stat checks alone are not an adversarial immutability guarantee. The guarantee is exact **captured** bytes, not atomic filesystem history or original authorship.

Store publication bytes outside tool-writable profile directories, with exclusive immutable objects and a DB reference. Reuse existing ID/private-file/buffer helpers as appropriate, but do not reuse existing attachments unchanged: attachment storage is under the profile workspace and the loader checks org/profile rather than session (`packages/core/src/attachments/store.ts:7–34`; `apps/server/src/services/attachment-service.ts:124–159`). Existing share snapshots likewise permit refresh. A forged history row, artifact sidecar, custom-tool output, guessed ID, or changed source file must not create or alter publication authority.

Make server publication creation idempotent for one trusted execution and output ordinal; this prevents duplicate records on persistence/transport recovery without re-running the producer. Commit/persistence failure must preserve the file/effect receipt and report publication pending/failed, never silently report delivered. Do not roll back user output files merely because a receipt write failed. Blob cleanup can remove only unreferenced staging objects. All output-size limits and capture failures must be explicit; avoid pretending existing arbitrary-size shell outputs have a new universal guarantee.

The minimal dependency seam is an optional server-injected publication capability on `ToolContext`, closed over the authorized actor/session and a distinct execution ID. Core tools submit bytes/actual path; they do not import the server DB or choose owner IDs. Stage the publication while a producer runs and finalize it only after the protected executor recognizes a successful complete result. A later throw/failed result cannot auto-deliver a previously staged file. Standalone core/agent consumers without this capability retain file creation and descriptive metadata, explicitly without server publication authority. Production channel sessions must have the capability configured before the strict cutover. Native subscription tool dispatch uses the same executor/capability; this must not add a native inference retry or replace the provider's context lifecycle.

## Feasible phases and guarantees

**Phase 1 — add the boundary and adopt native byte producers.** Add the trusted publisher, persisted records, private snapshot reads, additive client fields, and producer hooks for file/DOCX/PPTX/spreadsheet/Office/PDF/image/browser. Preserve existing workspace paths, versioning, return data, sidecars, previews and ordinary automatic delivery. Add `workspaceObservations` for directory scans with no producer session claim; do not emit a new publication for unrelated/no-write tools. Initially this can run in comparison/diagnostic mode while consumers are migrated, but that mode is explicitly **not the race fix**. Do not activate strict worker publication authorization until Phase 2's compute path and all consumers are ready.

**Phase 2 — preserve Bash/Python/custom output delivery, then switch the complete flow.** Keep their current workspace and native subprocess lifecycle. Support explicit output paths on the operation or a small `publish_artifact`/save-reference tool using trusted execution context. At successful return, selected outputs go through bounded capture. Keep full workspace scans as observations for useful feedback; neither a diff nor “the only/newest file” auto-selects a deliverable. A completed final answer can nominate specific file delivery paths, but a bare incidental mention/code example must not be treated as user permission. Prefer a structured runtime delivery-intent field or explicit tool action, validated against current task/channel authority; text extraction can propose candidates only. No external public-share authority is inferred from that nomination.

For ordinary compute tasks that use the existing save-artifact workflow, expose the generic publication capability and return publication receipts without a new user confirmation. A single bounded follow-up may ask the agent to select intended deliverables when a file-producing request finishes with only observations; it is an optional compatibility aid with extra model cost, not deterministic success. If there is no authorized, unambiguous selection, report “file saved, delivery not confirmed” and keep it visible in the authorized workspace UI. It is impossible to preserve today's unconditional “send every changed file” behavior and simultaneously remove this race without stronger write isolation. This is an explicit correctness change for ambiguous/unclaimed files, not removal of Bash/Python delivery. Do not deploy claiming complete automatic parity until actual ordinary compute/Office/channel flows pass.

After this path is covered, switch new-version worker authorization, events and channel delivery atomically to publication IDs/snapshot bytes. Preserve old `path` response fields for display/editing. A legacy path API may resolve to an unambiguous publication in the authorized session; multiple versions require the publication ID rather than choosing a global latest file. New clients send IDs. User-visible final paths bind to the actual returned destination; clients should open the publication snapshot for that message and offer the working path separately where useful.

**Phase 3 — optional compute staging for more deterministic automatic output discovery.** An execution-owned output directory with explicit declared output selection can reduce dependence on a final nomination. A dedicated staging directory alone is not a write-authorship boundary when every process has the same filesystem credentials or broad workspace write roots. Stronger isolation requires OS-enforced output namespaces/read/write roots and preventing surviving descendants from altering published bytes; publishing still copies to immutable server storage. Transparently remapping all relative `artifacts/` writes for arbitrary shell code requires filesystem/workspace virtualization and is not the minimal patch. Do not silently change cwd, break source edits, copy the entire workspace, or serialize all tools as a shortcut. This phase is optional for the exact snapshot/publication invariant and must have its own compatibility review.

## Legacy behavior and migration

Keep all existing messages/files/sidecars/public links and their recorded dates untouched. Legacy embedded scan artifacts are indistinguishable from genuine producer declarations, so **there is no honest automatic backfill of historical session authorship or old byte hashes**. Display them as legacy path references; ordinary profile read permissions continue to apply. Do not rewrite them into verified publications.

For new channel delivery of a legacy file, require a currently authorized explicit path/publication action (including a user-requested reattach resolved from that conversation), capture the current bytes, and record a new publication now with `legacy_republished_now`. If a filename is absent or competing legacy candidates are ambiguous, request a concrete selection instead of enumerating another session's files. Old worker auto-read/share grants derived solely from directory-scan history must stop being sufficient after the cutover; preserving them forever preserves the defect. This is the unavoidable security-compatibility tradeoff and should be documented, not hidden by a permissive fallback. Existing public snapshots retain their existing revoke/refresh contract; no background migration republishes them or makes private files public.

## Behavior gates, using existing tests as foundations

Read-only inspection found useful coverage already: successful sidecar/unpaired Office/image/browser extraction and streamed fallback (`packages/core/src/channel-artifacts.test.ts:49–739`); failed partial-output suppression (`packages/core/src/tools/failed-artifacts.test.ts:19–146`); concurrent complete-version writes/source preservation and file guards (`packages/core/src/tools/pdf-document.test.ts:155–256`); raw-byte downloads (`packages/core/src/artifacts.test.ts:115`); live HTTP reauthorization and replaced-conversation checks (`apps/platform/discord/src/channel-artifact-authorization.test.ts:176–299`; `apps/platform/telegram/src/channel-artifact-flow.test.ts:163–261`). These tests do not currently establish the new publication boundary. None was run in this follow-up.

Required additions before cutover: the three existing barrier cases through actual persisted publication + HTTP/channel reads; distinct session/user/org and guessed-ID negatives; forged custom receipts and sidecars; same-path rewrite after publication still serves the recorded digest; read-versus-share byte equality; fail/abort after writing leaves files but no committed auto-delivery; publish/DB failure and idempotent receipt recovery without producer retry; explicit existing-file delivery; native Bash and Python XLSX/PDF auto-delivery through actual sandboxed execution; all Office tools retaining versioned paths and `.sources` exclusion; legacy republish policy and no silent trust upgrade; interrupted streaming preview never becoming publication; multi-process/symlink/parent-rename/descendant writer capture tests; membership/channel/session revocation still blocks delivery. Generic fixtures suffice—no benchmark/task-specific output schemas or semantic correctness claims.

Implementation cost is mainly one bounded byte capture/hash/snapshot per deliverable plus an additive DB/API/client path. Byte-producing tools avoid rereads; compute outputs require capture and possibly one bounded selection turn. Storage retention/cleanup is additive and must be accounted for. No new unconditional critic, global workspace mutex, model-specific heuristic, or inference retry is required.
