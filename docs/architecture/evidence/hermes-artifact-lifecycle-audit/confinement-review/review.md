# Artifact publication: actual compute boundary and honest immutability claim

Read-only source review. Atlas already applies OS filesystem confinement to ordinary native Bash/Python and default custom JavaScript execution. `workspaceRoot` is not merely cwd for these paths. However, neither a new directory nor a write-once application API makes bytes immutable against unrestricted host code with the same OS identity. The publication design should state both facts explicitly. No escape execution, tests, provider calls or production changes were performed for this review.

## Source evidence

All relative paths below are under `/Users/apriansyahrs/Documents/Code/atlas`; exact bytes are hashed in source-bindings.json.

- `packages/core/src/tools/context.ts:6–33` only validates/derives the absolute workspace path. It alone is not the security mechanism. Bash calls `prepareRestrictedProcess` at `apps/server/src/tools/bash.ts:165–180`; Python calls it at `apps/server/src/tools/python-execute-tool.ts:135–157`. Both actually spawn the prepared launcher, with no native host fallback.
- `apps/server/src/services/restricted-process.ts:133–205` canonicalizes the workspace and cwd, denies outside cwd, assigns a private temporary HOME, and uses macOS sandbox-exec with default denial plus workspace/temp write access. Runtime software roots are read-only; runtime-root widening into Atlas configuration/profile trees is rejected at98–129. Linux installs Landlock ABI3+ before exec (`restricted-process-linux.c:37–80`), allows writes only in admitted workspace/temp roots, uses no_new_privs, and fails closed if rules or inherited-descriptor closure fail. Unsupported hosts are rejected (`restricted-process.ts:249–253`).
- `apps/server/src/services/javascript-tool-loader.ts:85–96,156–193` inspects and executes custom modules in a child, rather than importing their top-level code into the server. The runner receives only the workspaceRoot field (`javascript-tool-runner.js:45–49`), not a trusted server publication capability. The module subtree is read-only and workspace/temp are writable under default macOS or Linux policies (`custom-tool-subprocess.ts:226–267,318–349`; `javascript-tool-sandbox-linux.c:344–420`). Thus a tenant administrator's ordinary custom tool is also confined by default.
- There is an explicit exception: `ATLAS_ALLOW_UNSANDBOXED_CUSTOM_TOOLS=1` bypasses that custom-tool OS launcher when requireSandbox is not set (`custom-tool-subprocess.ts:213–222`). Production loader calls do not set requireSandbox. This host opt-in removes the filesystem guarantee for arbitrary custom code; an allowlisted environment and separate process are not substitutes. Bash/Python have no equivalent fallback in the inspected code.
- Bash/Python kill their process group on completion/abort (`bash.ts:193–247`; `python-execute-tool.ts:173–214`). That is not proof that every independently detached descendant has terminated. All same-profile executions still share the same writable workspace, so OS confinement does not fix execution authorship or concurrent workspace races. Custom-tool timeout handling targets its direct child (`custom-tool-subprocess.ts:70–116`), not a complete descendant namespace.

## What the proposed publication can honestly guarantee

| Actor / failure mode | Supported prospective claim | Limit |
|---|---|---|
| Ordinary concurrent workspace writers | Capturing exact bytes once into a new server-managed object lets later delivery remain stable when the editable source path is overwritten. | Capture still needs the bounded regular-file/parent-race checks already specified. A chosen snapshot does not prove which session authored the source. |
| Model-controlled Bash/Python or default sandboxed custom JS, even under the server UID | A snapshot outside **every admitted tool write root** is protected from their direct filesystem writes by the existing OS policy, conditional on supported launcher enforcement and trusted root configuration. Keeping it outside admitted read roots also protects direct file reads. | The publication store must not be placed in a profile, per-tool temporary directory, or an exposed runtime/module subtree. Do not grant a handle or publication mutation capability to untrusted code. This is scoped filesystem protection, not a claim of a universal hostile-code sandbox. |
| Unrestricted host process, server bug, host administrator, or custom JS under the unsafe opt-in | Exclusive object creation plus publisher API rules can provide application-level write-once semantics and SHA verification can detect byte tampering if the trusted record remains intact. | Same-UID code with filesystem access can usually chmod, rewrite or unlink ordinary files and may alter the DB too. Merely placing files elsewhere, mode0600/0444, an opaque name, or a content hash is not an adversarial immutable boundary. |

A stronger guarantee against unrestricted same-UID code needs a distinct storage authority: another OS identity/privileged broker with an authenticated narrow API, enforced object-store immutability, or an equivalent actual access-control boundary. That would be a separate implementation/deployment choice. Do not imply it already exists. Host administration and trusted in-process producer code remain within the trust base unless explicitly isolated. Tenant-admin-authored custom modules should not be called trusted server code merely because an admin authored them.

Network remains allowed by default for native compute and custom JS (`restricted-process.ts:136,205`; `custom-tool-subprocess.ts:349`); native ATLAS_PROCESS_NETWORK=deny is macOS-only and fails closed on other platforms. Therefore snapshot APIs still need current actor/org/profile/session authorization. The filesystem review alone does not certify arbitrary IPC, network services or all server entry points.

Recommended design wording: **“Publication stores one captured byte sequence in server-managed, write-once objects outside all admitted tool filesystem roots. Default OS-confined tools cannot directly mutate those objects; delivery resolves the authorized record and serves its bound bytes. This protects against workspace rewrites, not unrestricted host/admin code. Deployments enabling unsandboxed custom tools do not receive the tool-resistant filesystem guarantee.”**

## Small prospective verification gate

Existing source tests exercise actual Python/Bash outside-profile reads/writes, symlink/hardlink and inherited-descriptor rejection, runtime-root widening, and same-group background cleanup (`process-filesystem-isolation.test.ts:53–194`). Custom-tool tests cover outside-config access and read-only dependency trees (`javascript-tool-loader.test.ts:433–562`), but their helper can accept a fail-closed sandbox-unavailable result (`:21–39`); such a run proves denial rather than successful confinement. No tests were run here.

Before claiming publication immutability, run one supported-host scenario for each real native execution path: a server publication is created, the workspace source changes, later delivery still has the recorded digest; the tool's direct read/write/link/rename attempts against the private object are denied while an allowed workspace write succeeds. Cover a surviving/detached writer and concurrent capture separately. Verify the unsandboxed custom-tool opt-in yields an explicit lower-assurance deployment status rather than silently retaining the stronger claim. Reuse existing source-attribution/session-authorization gates; no unsafe host escape or hostile-code guarantee is needed.
