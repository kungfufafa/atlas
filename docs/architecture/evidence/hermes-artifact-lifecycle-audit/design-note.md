# Completion and artifact lifecycle: bounded source audit

Scope: current candidate3 Atlas production source and the pinned Hermes source at `/private/tmp/atlas-hermes-evaluation/source`. No model calls, current study outcomes, or holdout tasks inform this audit. This is a source audit, with the separate local artifact reproduction described below; it is not comparative performance evidence.

## Priorities

1. **P1 — a shared-directory change is incorrectly treated as session provenance.** Atlas derives each session's workspace from the same organization/profile directory (`packages/core/src/tools/context.ts:5–35`). The protected executor snapshots the complete `artifacts/` directory before and after every tool that is not `parallelSafe`, labels every changed file with the current session (`packages/core/src/tools/execution.ts:47–127,565–617`), and returns those references. A successful tool in session A can therefore observe a file written by concurrent session B and return it as A's artifact. Sequential mutation within one turn does not serialize independent sessions. Python repeats a workspace-wide before/after scan (`apps/server/src/tools/python-execute-tool.ts:132,237–280`). This matters beyond presentation: embedded tool artifacts enter `extractSessionArtifacts` (`packages/core/src/channel-artifacts.ts:599–632`), which builds the channel-worker session artifact allowlist (`apps/server/src/http/workspace-worker-artifacts.ts:4–15`). That extractor's own comment intends to prevent discovery of another session's files. The barrier reproduction uses controlled tool writes and actual protected execution; it does not assert an end-to-end channel exploit.

   Minimal safe direction: distinguish explicit producer-bound artifact receipts from opportunistic directory discoveries. Do not promote an unowned directory difference into a session authorization record. Prefer per-execution artifact staging or an execution-bound publication operation that records the actual resulting path and bytes. A process-local workspace mutex around the entire snapshot/tool/snapshot interval can mitigate one interleaving, but it is not complete provenance: other processes, shell descendants and untracked writers remain outside it; long-running tools serialize; nested same-workspace tools/approval waits can deadlock. Do not silently introduce that global lock as a complete fix. Preserve legitimate automatic artifact delivery when designing a replacement.

   Behavioral tests: two sessions sharing one profile with barrier-controlled writes; successful no-write A overlapping write B; serial control; rewrite/versioned output; another worker process; cancellation and failed partial output. Required invariant: only the producing execution's artifacts become its session's delivery references; no retry or lost effect.

2. **P1 — mechanically unfinished execution becomes a done task.** Atlas already detects repeated no-progress tools and a 100-iteration limit, then requests a tool-free truthful summary (`packages/agent/src/chat.ts:1160–1254`). Both normal final text and that limit/stall summary return a string with turn outcome `completed` (`:1122–1127,1253–1267`). `AgentService.runTaskPrompt` returns the session string (`apps/server/src/services/agent-service.ts:2544–2576`), and `TaskRunner.run` marks any nonthrowing result `done` (`apps/server/src/services/task-runner.ts:39–48`). Thus a perfectly truthful “work remains unfinished because execution stopped” can still produce a done task. This is a loss of runtime stop semantics, not a claim that every tool error or refusal means a failed user task.

   Minimal direction: carry a typed terminal reason alongside the final text through the session/task boundary, preserving existing history, streaming and summary behavior. For mechanically known `iteration_limit`/`no_progress`, retain output and mark the task unfinished using an explicit supported state (the current task enum only has backlog/todo/in_progress/done/failed, `packages/core/src/contract.ts:1325–1333`; adding a blocked state requires a separate schema/UI decision). Do not infer task achievement from natural-language parsing or retry a native turn automatically. Tests should trigger repeated identical tool results with a deterministic provider stub and assert a truthful final is retained while the task does not become done; successful ordinary chat remains completed.

3. **P2 — artifact receipts are useful evidence, but physical delivery and semantic correctness are different.** The executor accepts declared artifact objects if they have a string path; those declarations take precedence over detected metadata (`packages/core/src/tools/execution.ts:130–143,588–617`). Chat artifact emission performs shape checks, not a fresh file/content verification (`packages/agent/src/chat.ts:1335–1394`). Builtin artifact writers already return the actual versioned output path (`packages/core/src/tools/builtin.ts:405–440`); a model ignoring it is not itself a path-resolution bug. Bind user-visible delivery to a canonical, scoped producer receipt and verify existence/type/size at publication or delivery; consider an immutable content identity when files can later change. This can catch nonexistent/stale/wrong-version paths, not prove a spreadsheet or report satisfies the user's instructions. Tests should cover a nonexistent declared path, changed file after publication, actual versioned path, and unambiguous successful delivery. Remote artifact types and mutable workspace files need an explicit contract before imposing local-file checks universally.

## Existing protections and the Hermes comparison

Atlas already retains individual failed tool receipts, avoids publishing artifacts from failed tool results, limits retry to explicitly opted-in safe reads, handles output-limit recovery conservatively, has durable approval/run leases, and cleans up native shell/Python process groups. These are implemented features; this note does not propose them as missing. A completed chat turn describes lifecycle completion and does not independently prove task correctness.

The pinned Hermes `agent/verification_stop.py:50–80` defaults verification-on-stop **OFF**, unless environment/config explicitly enables it; explicit `auto` is surface-dependent. The example config's comment around `cli-config.yaml.example:1170–1177` still describes `auto`, so runtime code is the authoritative default. When enabled, the guard reads passive edit/test evidence and can request at most two further verification attempts (`agent/verification_stop.py:158–225`); it does not run tests itself. Data/prose files are filtered, exceptions fail open, and a registered `pre_verify` hook is optional (`agent/turn_stop_gates.py:31–76`). Candidate answers are retained as interim output before a synthetic continuation (`:93–139`). At exhausted budget the finalizer can reuse the pending candidate (`agent/turn_finalizer.py:119–157`). This is a bounded coding nudge, not guaranteed correct completion or universal artifact validation.

A passive per-execution verification ledger could help Atlas present what was actually checked and whether a file changed afterward. An unconditional extra model critic is not the first fix: it adds tokens/latency, may change correct answers, cannot retract already streamed content, and supplies no guarantee across models, providers, or subscriptions. Fix deterministic ownership/status defects first; evaluate any optional bounded review against real user constraints and observable evidence, with costs and false-positive regressions measured separately.
