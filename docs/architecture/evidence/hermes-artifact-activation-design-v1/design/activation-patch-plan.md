# Ordinary persisted chat: concrete publication activation plan

This is a prospective patch plan, not an implementation or an activation approval. `C5` means `/Users/apriansyahrs/Documents/Code/atlas`, source `1b44dd862ed3dac305c1ebe86dabda28c0de085c6a1d9fc1f6f1eb5eaa7dca2d`. `assembly` means `/private/tmp/atlas-artifact-assembly-c5/source`, source `092cddfec661d7e35a8061f16e52d4389c158a3b64a7c102523b8a4b31b9233c`. Exact bindings accompany this report. Parent's per-turn principal interface below is a reported, still-developing contract; its scratch was not read or edited and its tests are not claimed here.

The smallest viable wiring patch uses one fresh authenticated turn preparation before `resolveSession`, forwards its immutable host options through both HTTP modes, and constructs one publication service per turn over a shared private-store factory. Leave `buildChatSession`'s default lifecycle unset. This avoids turning cached human tool context into worker authentication or accidentally enabling task callers that happen to reuse `resolveSession`.

**C5 cannot safely enable that patch today.** Missing pre-load/pre-spawn private-store admission must reject execution, not silently remove the publisher. The isolated components and new principal seam do not by themselves supply the actual filesystem grants. A restricted initial cohort may admit only verified implementations under a host-wide enforced boundary; unverified runtime kinds must fail before loading/running, and must not be described as supported file generation.

## Proposed patch surface, in dependency order

These are suggested implementation names, except the principal interface reported by parent. Build in a new scratch after explicit component assembly; no change listed here has been made.

1. **`services/publication-chat-runtime.ts` (new server composition adapter).** Inject `db`, `agent.canAccessSession`, one `getStore` factory and the host admission policy. Expose `prepareTurn(orgId, sessionId, actor)` returning an immutable `Pick<SendStreamOptions, 'toolExecutionGuard' | 'toolExecutionLifecycle'>`. Re-read the persisted session and explicitly admit ordinary `web`/`cli` human chat plus authenticated `telegram`/`discord`/`whatsapp` worker chat. Keep task/delegate/automation/playground unsupported; guests remain without executable tools. Create the principal before asking for storage or resolving executable tools. Validate the supported session channel from DB, not request metadata.
2. **`services/agent-service.ts`.** Store only the stateless runtime composition dependency, following existing service injection patterns. Expose `preparePublicationTurnOptions(orgId, sessionId, actor)` for the messages route, and invoke mandatory profile/code-load admission before `resolveProfileTools` resolves custom code or skills. Cache the resulting session as today, but never cache options, principal, controller, ordinals, snapshot promises or current signal. Required admission must still apply at the actual loaders/launchers across all entry points; this AgentService check is an early rejection, not the whole boundary.
3. **`http/routes/sessions.ts`.** After `beginSessionTurn` and before `resolveSession`, obtain the turn options in the existing cancellation-protected block. Thread that exact options object to non-stream send and `streamMessage`. Do not modify `SendMessageRequest` or expose new model/client actor fields. Preserve worker actor returned by `sessionActorFromAuth` unchanged.
4. **`http/shared.ts`.** Add the trusted options parameter to `streamMessage` without changing the positional timeout semantics used by tests (a trailing options object is a small compatible choice). Snapshot host hooks immediately; spread only those host fields, then set `signal: turnSignal`, which includes client cancellation, timeout, and registry cancellation. No asynchronous observer may replace the actual signal.
5. **`services/session-persistence.ts`.** Capture the two host hooks on entry and forward their fixed values through the persisted send wrapper while retaining checkpoint composition. This closes a wider wrapper lifetime than the agent package alone. No DB publication dependence on this wrapper's history-save success.
6. **`index.ts`, `http/context.ts`, and assembly `http/routes/artifact-publications.ts:98–111`.** Lift the existing reset-on-initialization-failure store promise into one server-owned factory using canonical `getUserConfigDir`. Inject that factory into publishing and consumer access. Do not retain an authorization-bearing service singleton. Consumer `createSessionPublicationAccess` must continue to authorize before `getStore`. Publication turn preparation must do the same. An enabled mode with absent DB/admission dependency must fail configuration/turn admission, rather than fall back to the legacy path. Bind store/admission lifetime to a clean server start; data restore must quiesce execution, invalidate cached store/admission state and repeat the boundary checks before access resumes (`index.ts` existing `onDataRestored` callback is the integration hook).

The already-developed parent seam supplies `createPublicationTurnPrincipal({ actor, agent, db, orgId, sessionId })`, returning `effectUserId`, an immutable original `invoker`, `scope`, `beforeToolCall`, `authorizePublication`, and `validateContext`. It also adds per-send `toolExecutionGuard(context, toolName?)` and `toolExecutionLifecycle | null`. Bind the actual frozen version before implementation; these names are not proof of a merged implementation.

The composition should behave as follows (pseudocode; admission methods below are requirements, not existing C5 APIs):

```ts
const principal = await createPublicationTurnPrincipal(trustedRequest);
await requireSupportedOrdinaryChat(principal.scope);
await admission.beforeResolve(principal.scope); // no code import before this
const store = await getStore();                 // after rights and host admission
const service = new ArtifactPublicationService(db, store,
  principal.authorizePublication);
const lifecycle = createArtifactPublicationLifecycle({
  service,
  admittedToolRoots: context => admission.rootsForActualExecution(context),
  onFinalized: observeSeparatePublicationOutcome,
});
return Object.freeze({
  toolExecutionGuard: async (context, toolName) => {
    await principal.validateContext(context);
    await principal.beforeToolCall();
    await admission.beforeTool(context, toolName);
  },
  toolExecutionLifecycle: lifecycle,
});
```

The reported `validateContext` may already perform the same current-access check as `beforeToolCall`; remove a duplicate read only after inspecting its frozen contract, never by dropping the required check. Existing version/role/channel guard still runs through the agent's composition. Lifecycle `begin` can additionally validate context but cannot substitute for the mandatory guard: its exceptions are intentionally swallowed by assembly `tool-loop.ts:59–69`, preserving tool effects when publication setup fails.

## Worker authorization and effect identity

C5 `SessionActor` has the worker channel at `agent-service.ts:390–395`. Worker session ACL at735–756 checks matching external channel, a real persisted human owner, current membership and a non-Super profile. `resolveSession:3299–3307` intentionally sets the tool context user to that human owner. The publisher identity should therefore use the principal's validated human effect user, while every session ACL continues to use the original authenticated worker user/channel. Do not rewrite a worker into a human SessionActor to make an equality check pass.

Consumer authorizer in assembly `artifact-publication-access.ts:13–69` binds `scope.actorId` to the requesting actor and then applies current session ACL. Its reader scope differs deliberately from the publication writer's effect identity. Use the principal's `authorizePublication` for the new writer; leave request-bound consumer access unchanged. Scope lookup in the DB is org/profile/session, and record creator identity is server-owned provenance, not a grant permitting only that same creator to read. Wrong org/profile/session, revoked membership, changed owner, archived organization or importing/missing profile must reject at turn preparation and again at relevant operation checkpoints. None of these async callbacks makes revocation atomic with blob I/O or SQL commit, and a chat run label is not a lease token.

## Fail-closed prerequisites: exact missing seam

The existing guard is just before `tool.run` inside retry execution (`C5 packages/core/src/tools/execution.ts:537–572`). It is after approval checks and the legacy workspace artifact pre-scan at565. Pre-scan/path safety and executable metadata therefore require earlier admission; a new guard does not mean no filesystem access happened before it.

- **Before module loading:** `AgentService.resolveProfileTools:5618` resolves stored custom tools; `tool-resolver.ts:99` loads JavaScript. Skills load at5711 and C5 `packages/core/src/skills/load-tool.ts:92` imports host code. `createSession` and `branchSession` build tools even before a message exists. Merge and verify the separately reviewed confined skill loader, or reject these executable assignments before load. Custom unsafe opt-out must not permit host code in the protected-store trust domain. Name matching alone cannot certify a tool: bind admission to the actual server-resolved definition/provenance, including tool-search catalog exposure.
- **Before any local MCP start:** C5 `mcp-client-manager.ts:61,142,303` creates transports during connect/test, including non-chat admin paths; service startup at `index.ts:197–202` and cached connections outlive a turn. A messages-only guard is too late. Merge the enforced pre-start policy or disable stdio creation/test/connect host-wide before storing protected bytes. Reject a stale pre-policy connection rather than treating its cached catalog as admission evidence.
- **Before each arbitrary-code spawn:** C5 `restricted-process.ts:133–207` resolves actual workspace, executable/runtime and fresh temporary roots; Bash spawns at`tools/bash.ts:180`, Python at`python-execute-tool.ts:153`. Custom JS prepares separate roots and can choose an unsafe branch at`custom-tool-subprocess.ts:213`. Assert store disjointness from the exact launch plan before spawn, including read roots, even for a tool that publishes nothing. Return/retain a server-owned admission receipt or registry entry from that same preparation, rather than reconstructing grants from context later.
- **At staging:** assembly `artifact-publication-lifecycle.ts:120` only calls `admittedToolRoots(capturedContext)`. Context currently has no opaque invocation admission handle; its shallow clone cannot certify dynamic roots, distinguish parallel invocation receipts by itself, or recover a deleted per-launch temp directory. This is a real API integration prerequisite. Bind an immutable grant record through trusted execution plumbing (not provider ID alone or tool JSON), validate it at admission, and use its already-validated canonical identities at staging. If keeping the current store's `realpath`-based check, account for cleanup explicitly; do not replace a vanished temp with its broad parent. Until implemented, fail closed for these unverified runtime kinds instead of returning only the profile root.
- **Shared host boundary:** Other profiles, admin tool tests, already-running processes and unsafe host modes can expose the same UID's private files. A flag on the publishing profile is insufficient. Apply policy before any such access throughout the deployment, on a clean transition, with explicit trust for fixed server code, document workers and native SDK internals. Browser's explicit no-sandbox and fixed PDF/LibreOffice host processes are not proved OS-excluded; either enforce that exclusion or state the narrower trusted-worker boundary. All admitted application file roots must be checked too: existing filesystem/search helpers can reconstruct profile root despite `context.workspaceRoot` narrowing. The sealed prior audit contains exact root arrays and source references; this plan does not invent a replacement allowlist.

These prerequisites do not require unrelated task/delegate publication features. They are necessary to protect ordinary chat's private objects from every actual local capability that can reach them. If the initial implementation supports only trusted in-process byte producers, enforce that narrower set before load/run and label Bash/Python/custom/skill/MCP publication unsupported until their receipts are wired.

## Delivery and initial scope

Assembly gives generated byte producers a byte-only publisher. Its server-only selected-file method is `ArtifactPublicationExecution.stageSelectedFile` (`artifact-publication-service.ts:49,142`), and it must retain `selected_workspace_capture` evidence. The current generic lifecycle exposes no selected-file capability or explicit selection route; wiring generated bytes does not automatically publish Bash/Python outputs. Do not use legacy changed-path scans, mutable workspace rereads, arbitrary returned `artifacts`, or copied model JSON as a selection authority. Add a deliberate server-scoped selection action separately before claiming those outputs are covered.

For the minimal ordinary-chat backend patch, committed publications remain discoverable through the additive DB-authoritative list/content routes after success, cancellation or history/distillation failure. Assembly `tool-loop.ts:77–107` can commit before distillation fails; C5 `session-persistence.ts:145–224` can fail after effects; neither may trigger producer replay. Preserve file receipts and report publication failure separately. `onFinalized` is non-blocking diagnostics and cannot be the only delivery index.

Existing `chat.ts:1362–1424`/`http/shared.ts:641` emits legacy `artifact_created` from raw artifact fields, and channel consumers still use their existing delivery paths. Keep that compatibility surface explicitly separate during backend integration. Full visible cutover must add a distinct authoritative publication event/list reconciliation and publication-ID content fetch to UI and worker delivery; do not relabel a legacy path event as an immutable snapshot. No claim of complete chat artifact experience is justified by the backend patch alone. No new UI or external send is authorized by this design audit.

## Focused acceptance for the next integration patch

Use the actual persisted wrapper and messages route, not only the agent package fixture. Proposed checks, none run here:

1. API/native × send/stream, human and worker, across two cached turns; original invoker survives, correct human effect identity is used, no old lifecycle/ordinal/signal leakage.
2. Reject wrong-channel worker, changed owner, revoked membership, viewer and wrong org/session before code load and again before effect/publication. Keep existing version/channel/approval guards and stream cancellation.
3. Prove missing/denied admission never runs a metadata import, stdio startup, pre-scan with an overlapping root, or actual tool. Include another profile and a pre-existing connection so scope is not cherry-picked.
4. Real dynamic-root overlap rejection at the prepared launcher, cleanup-aware grant retention, parallel invocation separation, and an unsafe opt-out denial. A mocked list of profile roots is insufficient evidence.
5. A committed output remains available via DB routes when distillation or history persistence fails; publication storage failure leaves the original file/effect receipt intact and does not replay a producer.
6. Explicit-null/no-option behavior on task/delegate/automation/playground, including those with a persisted session: no inherited publisher, no fabricated delivery scope. Existing execution behavior stays separate from publication support.
7. Snapshot host options through a delayed persisted wrapper, preserve native durable checkpoints, and prove a callback from a closed native dispatch cannot acquire a later turn's authority.
8. Assert generated-byte versus selected-capture eligibility and no automatic legacy path fallback; run the existing bounded producer/lifecycle/consumer tests after integrating, keeping owner/reviewer counts separate.

The final implementation review must bind the then-frozen principal, admission, assembly and consumer source versions. It makes no Hermes parity, atomic snapshot, universal revocation or durable ownership claim.
