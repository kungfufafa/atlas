Your agents get better at repeat work when they can **save what worked** as a [skill](/skills) — a short playbook the bot can follow next time.

**Self-improving skills** is Atlas's approach to that: agents can create and update profile skills after complex tasks, while your team keeps control when you need it.

## Why this matters

Without this, every win stays in one chat. The same debugging steps, deploy checklist, or customer workflow gets explained again from scratch.

With self-improving skills:

- **Less repeat explanation** — the agent captures a workflow once and reuses it when a similar request comes up.
- **Cleaner profiles** — procedures live in skills instead of bloating the main prompt.
- **Team safety** — Workspace Admins can require approval before a new or changed skill affects future behavior.
- **Safety net after complex work** — optional post-turn review can catch missed saves without silently changing skills.

Think of it as the agent learning *how to do the job*, while you decide whether that learning goes live immediately or waits for a quick review.

## How it works

```text
Complex task succeeds  →  Agent saves a skill (or review suggests one)  →  Skill matches on later chats
                              ↓
                    (optional) Workspace Admin approves
```

1. **During chat** — after a hard problem, recovery, or correction, the agent may offer to save the approach as a skill (for example, a deploy checklist or support triage flow).
2. **On demand with `/learn`** — turn notes, a URL, an attachment, or the workflow you just completed into a skill now.
3. **After complex turns (optional)** — when **post-turn skill review** is on, Atlas may review the finished turn in the background and either show an **Apply** suggestion in chat or stage a proposal for a Workspace Admin.
4. **On later turns** — when someone asks for something similar, Atlas can load that skill and follow the saved steps.
5. **Optional gate** — if write approval is on, skill changes wait in a proposal queue until a Workspace Admin approves or rejects them.

Skills hold **procedures** (how to do something). Profile memory holds **facts** about the user (preferences, context). Keep preferences in memory; keep repeatable workflows in skills.

## Where it works

| Channel | Agent can update skills? | Post-turn review? |
|---------|--------------------------|-------------------|
| **Web chat** | Yes | Yes (when enabled) |
| **CLI chat** | Yes | Yes (review may run; Apply is web-first) |
| **Telegram, WhatsApp, Discord** | No | No |
| **Automations / scheduled runs** | No | No |

Org **viewers** can read chat but cannot run agents, so they cannot trigger skill updates or Apply suggestions.

Default and Super Agent profiles include the skill-authoring capability after sync. Other profiles need the **manage-skills** skill assigned — see [Skills](/skills).

## Learn from sources

In web or CLI chat, type `/learn` followed by the source or workflow:

```text
/learn filing an expense: open the portal, attach the receipt, and submit
/learn https://docs.example.com/api/quickstart
/learn the REST client in my project docs, focus on auth and pagination
/learn how I just deployed the staging server
```

Bare `/learn` after a conversation distills the workflow you just completed. As the first message in a session, it asks for a source unless a file or image is attached.

Atlas gathers the source with tools assigned to the profile, then creates or updates a matching skill through `skill_manage`. Large sources become a focused `SKILL.md` with supporting `references/` files instead of one oversized instruction file. Source content is treated as untrusted data and cannot authorize tool calls or override your request.

`/learn` is available only in web and CLI chat when the active profile has **manage-skills** assigned. It is not expanded in Telegram, WhatsApp, Discord, automations, tasks, or sub-agents. Because URLs, files, and attachments are untrusted sources, `/learn` always stages a proposal for Workspace Admin review; it never changes a live skill directly, even when the normal write-approval gate is off.

## Write approval (optional)

By default, skill changes apply immediately. Turn on **write approval** when you want a human check before creates, edits, or deletes affect the live skill catalog — similar in spirit to [org memory](/org-memory) proposals, but for per-profile workflows.

### Turn it on

Workspace Admins: **System → Workspace → Skill write approval → Gate settings**.

- Flip the toggle to require approval for skill writes org-wide.
- Optionally pick a profile and override: inherit the org default, always require approval, or allow immediate writes for that agent only.

![Enable the org-wide skill write approval gate and optional per-profile overrides](/screenshots/skill-write-approval-gate.png)

When the gate is **off**, nothing changes — agents update skills directly, as before.

### Review proposals

When approval is required, agents still *propose* skill changes during chat. Those proposals appear under **Proposals** on the same card (or via a notification link).

![Pending skill proposals on the Proposals tab](/screenshots/skill-write-approval-proposals.png)

Open **Review** to see the full skill content (or the before/after for an edit). **Approve** applies the change; **Reject** discards it with no effect on live skills.

![Review dialog — preview skill content and approve or reject](/screenshots/skill-write-approval-review.png)

Atlas flags suspicious patterns in proposals the same way it does for org memory — worth a closer look before approving.

Workspace Admins managing a specific bot can also open **Agent → Profiles**, select the profile, and use the **Proposals** tab there.

## Post-turn skill review (optional)

In-session saves can still miss a good workflow: the agent finishes a long tool-heavy turn and never crystallizes a skill. **Post-turn skill review** is an opt-in safety net for that case.

### Turn it on

Workspace Admins: **System → Workspace**, on the **Post-turn skill review** card (next to Skill write approval).

- Default is **off** (no extra review pass).
- Optionally override per profile: inherit the org default, always review, or never review for that bot.

When enabled, after a **successful** web or CLI turn that looks complex (many tool calls, or a tool error recovery) — and only if the agent did **not** already save a skill that turn — Atlas runs a lightweight background review. Chat is not blocked while that runs. It uses an extra model call on eligible turns, so leave it off unless you want the safety net.

### What you see (review × write approval)

| | **Write approval off** | **Write approval on** |
|---|---|---|
| **Post-turn review off** | No background pass | No background pass |
| **Post-turn review on** | Chat shows a suggestion with preview + **Apply** — nothing is written until you Apply | Review stages a proposal; chat shows a pending-admin notice; live skill waits for Workspace Admin approval |

Unlike some other agents that auto-write skills in the background when approval is off, Atlas **never silent-writes** from post-turn review. Gate off means you still choose **Apply**; gate on means an admin must approve.

Suggestions appear as a chat UI card (not as a message in the conversation history the model will see next turn). Ignore a suggestion by leaving it; there is no separate reject queue for suggestions.

## Consolidate overlapping skills (optional)

As a profile learns, two skills can begin covering the same workflow. Workspace Admins can turn on **Skill consolidation** under **System → Workspace**, optionally override it for one profile, and choose **Consolidate now**.

Atlas looks only at enabled profile-owned skills written by an agent or human. It skips bundled and global skills, pending proposals, recently changed or heavily used skills, and profiles referenced by active automations or unfinished tasks. Candidate counts and source sizes are bounded before a model sees them.

Every result is a proposal, even when normal skill write approval is off. Open **Proposals** to preview the rewritten winner and the exact loser skills. Approval rechecks their identities and content versions, updates the winner, then archives and unassigns the losers as one guarded operation. Rejecting leaves every live skill unchanged.

After opt-in, the automation worker checks eligible workspaces on its existing five-minute poll and runs consolidation at most once every seven days. The durable schedule survives worker or server restarts, and one workspace failure does not delay other automations. **Consolidate now** remains available when you want an immediate review. Scheduled runs still only create proposals; they never change, unassign, or archive a live skill until a Workspace Admin approves.

## Who can do what

| Role | Chat and trigger skill updates | Apply post-turn suggestions | Approve or reject proposals | Change gate / review settings |
|------|-------------------------------|----------------------------|----------------------------|------------------------------|
| **Workspace Admin** | Yes | Yes | Yes | Yes |
| **Member** | Yes | Yes | No | No |
| **Viewer** | No (read-only chat) | No | No | No |
| **Superadmin** | Yes | Yes | Yes | Yes |

## Skills vs org memory

Both help agents stay consistent across your team, but they solve different problems:

| | **Profile skills** | **Org memory** |
|---|---|---|
| **What it stores** | Repeatable workflows for one bot | Shared facts for the whole org |
| **Example** | "How we triage support tickets" | "Support hours are 9–6 SGT" |
| **Who approves agent writes** | Optional — only when write approval is on | Always — members propose, admins approve |
| **Where admins manage it** | **System → Organization → Skill write approval** | **System → Organization → Org Memory** |

Use org memory for facts everyone should know. Use skills for how a specific bot should run a task.

## See which skills are used

After your team has been chatting for a while, you may wonder which skills actually help and which just sit on the shelf. Atlas tracks that automatically for each **assigned** skill on a profile.

Open **Agent → Profiles**, select a bot, and scroll to **Skills**. Each skill shows a short hint such as **Last matched 2 days ago · 5 uses**, or **Never matched** when it has not been selected for a turn yet. Skills with no match in the last 30 days get an **Unused** badge — that is advisory only; nothing is deleted or archived automatically. **Bundled system skills** (shipped with Atlas, such as `manage-skills` and `save-artifact`) never get the Unused badge; they stay assigned by design.

Click a skill to open its detail dialog for the full breakdown:

- **Created by** — whether the skill came from an agent, a human admin, or the bundled library
- **Catalog views** — how often the skill appeared in the bot's skill list during chat (counted once per chat session)
- **Matches** — how often the skill was actually used on a user message
- **Updates** — how often the skill content was patched (including after an approved proposal)

These numbers update during **web** and **CLI** chat. They do not change from Telegram, WhatsApp, Discord, or automations — those channels do not run the skill-authoring flow today.

Skill consolidation is opt-in and proposal-only. It never archives an unused skill merely because it is old; it proposes merging only when eligible skills overlap. See [Consolidate overlapping skills](#consolidate-overlapping-skills-optional).
