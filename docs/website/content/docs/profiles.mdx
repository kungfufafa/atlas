A **profile** is an agent definition Atlas runs for a session.

It answers one practical question: **which agent should respond, and what is its role?**

Profiles belong to a **workspace**. Switching workspaces shows only that workspace's agents.

## Super Agent, Default Agent, new agent

| Agent | Role |
|---|---|
| **Super Agent** | The orchestrator. Creates other agents, assigns tools, writes host tools, and runs workspace shell work. Visible to Superadmins and Workspace Admins in that workspace. |
| **Default Agent** | Ready to use. Full work toolkit (search, files, research, documents) so the team can chat immediately. |
| **New agent** | Custom identity. Same work toolkit as Default Agent (search, files, research, documents). Super Agent extras (bash, host tools) stay off unless you assign them. |

Use **Default Agent** to get work done. Use **Super Agent** to build and operate the team. Create a **new agent** when a role needs its own personality — it already has the same work tools as Default Agent.

## Default profile per organization

Atlas does **not** share one global `default` agent across every org.

When an organization is created — including the first org at install — Atlas automatically:

1. Creates one **default profile** for that org (`isDefault: true`)
2. Assigns the standard builtin tool set (web search, file tools, email, and the rest)
3. Initializes its soul directory on disk

That profile is named **Default Agent** and gets a unique id (not a fixed string like `default`).

| What | Behavior |
|------|----------|
| Default profile | Exactly one per org, marked with `isDefault` — ready to use |
| Super Agent | Orchestrator; Superadmins and Workspace Admins in that workspace |
| Additional orgs | Each gets its own default profile and isolated on-disk data |

If a session or channel config omits a profile id — or names one that does not exist in the active org — Atlas falls back to that org's default profile.

### New custom profiles

Superadmins and Workspace Admins create profiles inside the **active workspace**. Each new profile gets its own soul directory and starts with the same work toolkit as Default Agent (search, research, files, documents, python) when those builtins are available. Super Agent extras such as `bash` stay off until you assign them. Add MCP servers and extra skills from the dashboard.

Super Agent can also create profiles from chat using a confirm-first factory. For profile-creation requests, it drafts soul files and a tool plan in chat, waits for your explicit OK, then calls `create_profile`. New profiles keep `MEMORY.md` empty and receive the Default Agent work toolkit automatically; `bash`, image generation, and host-tool authoring still need an explicit ask. On the Profiles page, use **Ask Super Agent** (empty state or create dialog) when a Super Agent profile exists.

Workspace Admins can also ask Super Agent to update an existing profile. It reads the current profile, shows the exact proposed changes, and waits for confirmation in a later message before applying them. It can update the name, model, stored prompt, skill-governance overrides, and the four soul files. Fields you do not approve remain unchanged, including skill write approval. Profile id, workspace ownership, default/Super Agent status, assignments, and credentials cannot be changed through this tool.

Super Agent can hand coding tasks to a dedicated coding agent via the `coding-agent` skill and `bash`. See [Coding agent](/coding-agent).

## What a profile contains

| Field | What it means |
|------|----------------|
| `id` | Stable unique profile id |
| `name` | Human-friendly label shown in the UI |
| `model` | Optional model selection for this profile |
| `systemPrompt` | Base instructions stored in the database |
| `isSuper` | Marks the profile as a super profile with elevated behavior |
| `isDefault` | Marks the org's default profile used when none is specified |
| `tools` | Builtin or custom tools the profile is allowed to use |
| `mcpServers` | MCP servers available to the profile |
| `skills` | Reusable instructions assigned to the profile |
| `hasAvatar` | Whether the profile has a custom avatar |
| `soulActive` | Whether soul files are present and active |

## What a good profile usually represents

One profile should map to one clear purpose. Create another profile when you need different instructions, tools, tone, or knowledge.

## How profiles affect replies

When a chat runs with a profile, Atlas builds the agent context in this order:

1. Start with the profile's `systemPrompt`
2. If soul files exist, compose them into the main system prompt
3. Append the assigned skills catalog
4. Append the knowledge base catalog
5. Append org memory summary for non-viewers (see [Org memory](/org-memory))
6. Expose only the tools allowed for that profile

So a profile is not just a name. It controls both:

- **How the agent behaves**
- **What the agent is allowed to do**

For the full prompt assembly flow, see [Agent prompt](/agent-prompt).

## Soul vs system prompt

Profiles support two layers of instruction:

| Layer | Best for |
|------|----------|
| `systemPrompt` | Quick base instructions stored in the database |
| Soul files | Richer identity, style, operating rules, and memory on disk |

Soul files, avatars, knowledge-base documents, artifacts, and profile-scoped skills all live under an org-scoped path:

```text
~/.atlas/orgs/{orgId}/profiles/{profileId}/
```

Supported soul files:

| File | Purpose |
|------|---------|
| `SOUL.md` | Identity |
| `STYLE.md` | Writing voice |
| `INSTRUCTIONS.md` | Operating rules |
| `MEMORY.md` | Continuity across sessions |

Archived memory lives alongside soul files at `memory-archive/` (monthly `.md` files). It is not part of the soul stack loaded into chat.

Profile-scoped skills are stored at:

```text
~/.atlas/orgs/{orgId}/profiles/{profileId}/skills/
```

Artifacts are files your agent creates and saves for you (reports, documents, generated text). They are stored at:

```text
~/.atlas/orgs/{orgId}/profiles/{profileId}/artifacts/
```

Workspace Admins can correct Markdown, CSV, and TSV artifacts directly from **Files → Artifacts**. Saves are conflict-checked, so a newer agent or teammate update is not silently overwritten. Existing public share links remain snapshots; publish the artifact again to share an edited version. See [Artifact saves](/builtin-tools#artifact-saves).

If you want richer personality and clearer long-term behavior, use soul files. If you only need a quick setup, the stored `systemPrompt` may be enough.

Superadmin data exports include these workspace/profile directories as part of the full Atlas data-root ZIP.
Restoring an export replaces the local data root after preview and confirmation; it is not a per-profile merge.

### Default Agent soul stack

New organizations receive a **pre-filled** soul stack for Default Agent — identity, voice, operating rules, and memory — not blank placeholders. Customize files in the dashboard Prompt tab. The database `systemPrompt` field is for optional operational overrides when it differs from `SOUL.md`; fresh installs leave it empty so identity lives in soul files alone.

Existing profiles keep customized soul files. On server startup, `ensureSoulScaffolded()` fills **missing or empty** soul files and upgrades **legacy placeholder** `SOUL.md` content (the old `# Your Name` scaffold) to the current Default Agent template. Customized souls are not overwritten.

## Model selection

Each profile can optionally select its own model.

| Field | Meaning |
|------|---------|
| `model` | Uses a specific model for this profile instead of the workspace default |

## Knowledge base and memory

Profiles keep their own context on disk under the org-scoped profile directory:

- **Knowledge base** documents for searchable reference material
- **Inherited knowledge sources** for shared product references, such as the Atlas documentation
- **`MEMORY.md`** for active facts and continuity the agent should remember across sessions
- **`memory-archive/`** for facts moved out of active memory without deleting them
- **Artifacts** — files your agent creates and saves for you (reports, documents, generated text)

At the **organization** level (not inside a profile directory), [org memory](/org-memory) stores shared facts every profile in the org sees — admin-curated, distinct from per-profile `MEMORY.md`.

Memory writes and archives use bundled skills (`update-profile-memory`, `archive-profile-memory`) with the profile's file tools — not separate memory builtins. Artifact saves use `save-artifact` with `write_file`. Default and super-agent profiles receive these skills automatically when they are installed on the server.

| Store | Loaded into chat | How agents write |
|-------|------------------|------------------|
| Workspace memory | Yes (appended as `## Org Memory` for non-viewers) | Workspace Admins via Settings or API — see [Workspace memory](/org-memory) |
| `MEMORY.md` | Yes (via soul stack) | `update-profile-memory` skill + `read_file` / `edit_file` / `write_file` |
| `memory-archive/` | No | `archive-profile-memory` skill + file tools |
| `artifacts/` | No (dashboard, download API, web chat preview) | `save-artifact` skill + `write_file` or `write_docx` |
| Knowledge base | Via `knowledge_base_search` when assigned | Upload via dashboard; search at runtime |
| Profile skills | Via skill matcher when relevant | `manage-skills` skill or dashboard |

Active `MEMORY.md` has a **4096-byte** soft limit. When it is full, the agent should archive old bullets before adding new ones.

Org memory has separate limits: **8192 bytes** for the live file and **2048 bytes** for the injected summary. See [Org memory](/org-memory).

This data is isolated per org and per profile. Two orgs never read or write the same directory, even if profile ids happen to match.

Each profile also sees the default Atlas documentation source in the Knowledge tab:

```text
https://kungfufafa.github.io/atlas/llms.txt
```

When a user asks about Atlas setup, profiles, tools, orgs, integrations, API, or troubleshooting, the agent should `web_fetch` that index first, then `web_fetch` the matching `.md` page (for example `telegram.md` for Telegram setup). Do not use `knowledge_base_search` for inherited documentation — that tool only searches uploaded files.

## Multi-tenant behavior

Profiles are tenant-owned data inside an organization:

| Rule | Detail |
|------|--------|
| Listing | `GET /v1/profiles` returns only profiles for the active org |
| Lookup | Requesting another org's profile id returns not found |
| Sessions | Bind to one profile within the active org |
| Tool access | Scoped per profile |
| Mutations | Workspace Admin or Superadmin; members chat with workspace profiles |

Workspace Admins manage members and profiles in their active workspace. Superadmins can do the same after switching to that workspace.

## When to create multiple profiles

Create separate profiles when you need different:

- Agent identities
- Safety or operating rules
- Tool access
- Knowledge bases
- Models

## Clone a profile

Tuning an agent and then wanting a close variant is common, so **Profiles** has a **Clone** button on the selected profile. It creates `{name} (copy)` in the same organization and selects it.

The clone gets its own soul directory, avatar and knowledge base, and starts with the same system prompt, model, tools, skills, MCP servers and Composio toolkits as the source. It never becomes the organization default.

Two things are deliberately not carried over:

- `MEMORY.md` starts empty, so the clone does not inherit the source's continuity
- Super Agent cannot be cloned, the same rule that stops it being deleted

## Move one profile between workspaces

Workspace Admins—and Superadmins after switching into a workspace—can move a
standard profile with a profile-pack ZIP.

To export, select the profile on **Profiles** and choose **Export ZIP**. To
import, switch to the destination workspace, choose **Import profile**, select
the ZIP, review the preview, and name the new profile. Atlas always creates a
new standard profile; an imported profile cannot become Super Agent or the
workspace default.

The pack carries the profile instructions, soul files, active memory, avatar,
knowledge-base documents, and profile skills. When a Superadmin exports it, the
pack may also include source for assigned custom JavaScript tools; exports made
by Workspace Admins never include host-level tool source. It does not carry
generated artifacts, archived memory, provider credentials, MCP configuration
or secrets, or Composio connections.
Tool, skill, MCP, and Composio assignments reconnect only when a matching
resource is already available in the destination workspace; the preview lists
anything Atlas will skip. A profile model is restored only when that model is
available there, otherwise the workspace default is used.

Profile-pack ZIPs can still contain sensitive text written by users in soul,
memory, knowledge-base, or skill files. Handle them as workspace data even
though Atlas-managed provider and connection credentials are excluded.

Profile packs are designed for moving one agent, not for disaster recovery.
For a whole-install backup, see [Backup and restore](/backup-restore).
