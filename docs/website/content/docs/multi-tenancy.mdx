title: "How Multi-tenancy Works"
description: "Learn how workspaces, roles, and tenant isolation work in Atlas."
---

Atlas can run more than one team or customer on the same deployment. One
**workspace** is one tenant boundary. Each workspace keeps its own profiles,
sessions, members, provider credentials, model settings, assignments, memory,
and usage data.

## Why this matters

Multi-tenancy lets you run one Atlas server without mixing teams together.
Workspace A cannot read Workspace B's chat, provider credentials, profiles, or
settings—even if someone knows a resource ID from the other workspace.

## Roles

| Role | Scope | Capabilities |
|---|---|---|
| Superadmin | Entire system | Create and switch workspaces; same in-workspace admin as Workspace Admin after switching; host install, export, and public URL |
| Workspace Admin | One workspace | Full admin of that workspace only — including Super Agent, Files, MCP, tools, skills, members, providers, and integrations |
| Member | One workspace | Chat with profiles and use assigned workspace capabilities |
| Viewer | One workspace | Read chat history only; no agent invocation or mutations |

Workspace Admins have the complete admin surface **inside their active
workspace**. Superadmins have that same surface after switching into a
workspace, plus the ability to create other workspaces and run host-level
operations (data export, public web URL, host worker install).

Members chat, run Agent Work, and connect their own Composio apps. Viewers
open **Chats** to read history; they cannot send messages, start Agent Work,
or change workspace settings.

## Invite your team

After [first-time setup](/first-time-setup), a Workspace Admin (or Superadmin
in that workspace) adds people from **System → Workspace**.

1. Open **System → Workspace**.
2. Choose **Invite** and pick Workspace Admin, Member, or Viewer.
3. Copy the invite link and send it to the person.
4. They open the link, set a password, and join that workspace.

If you need an account immediately, use **Add member** instead. Atlas shows a
temporary password once — share the email and password, then ask them to
change it after the first sign-in.

People who already have an invite can also open **Sign in → Have an invite?**
and paste the link.

## First-time setup

1. Create the first Superadmin.
2. Atlas creates the first workspace.
3. Configure that workspace's AI provider.
4. Invite people as Workspace Admin, Member, or Viewer.
5. The Superadmin can create more workspaces later.

## Choosing workspace boundaries

Use separate workspaces for different customers, internal teams, environments,
or privacy boundaries. If one team needs multiple assistants while sharing the
same people and data boundary, use multiple [profiles](/profiles) in one
workspace.

Workspace Admins configure providers, profiles, Super Agent, files, tools, MCP,
and skills only in their active workspace. Creating additional workspaces, data
import/export, the public web URL, and host installation remain Superadmin-only.

## System page

**System** always reflects the **active workspace**, so switching workspaces
replaces the numbers and lists instead of mixing teams together.

| Tab | What you see |
|---|---|
| **Status** | LLM usage, scheduled automations, running jobs, and this workspace's Telegram / WhatsApp / Discord workers |
| **Workspace** | Members, skill-approval settings, and workspace memory |
| **Tools** | Builtin catalog plus assignment to profiles in this workspace |
| **MCP** | Servers registered in this workspace, with keys that stay here |

Superadmins see the same in-workspace Status page after switching. Usage
breakdowns stay inside the selected workspace — they do not include other
workspaces' tokens or spend. Channel bots and MCP servers on this page are the
ones configured for this workspace only.
