Use WhatsApp when you want the same Atlas agent available from your phone in a private chat or team group.

The WhatsApp bridge talks to the same Atlas server as the web app and CLI. It is a chat channel, not a separate agent system.

## Good use cases

WhatsApp works well for:

- quick questions while away from your desk
- using one Atlas profile from phone and web
- private chats with authorized users
- group conversations where the agent should join only when addressed
- lightweight status checks and short back-and-forth conversations

## What WhatsApp can do

With WhatsApp enabled, users can:

- chat with an Atlas profile in a private WhatsApp chat or group
- send photos, voice notes, and supported documents the same way as in the web app
- get saved files back in the chat, not only as a link
- switch org with commands
- start a new conversation or clear history
- stop an in-progress reply
- receive replies with simple WhatsApp-friendly formatting

## Channel controls

Workspace administrators can open **Integrations → WhatsApp → Channel controls** to manage **Channel enabled**, **Approval buttons**, and **Native actions**. Enable the actions your team needs, then choose **Save controls**. The replying profile also needs the `channel_action` tool.

WhatsApp supports reactions, polls, editing or deleting its own session messages, and saved media delivery in the current authorized chat. Polls do not offer anonymous voting or an automatic closing time through this bridge. Topic, thread, and pin actions are unavailable.

Use **Direct messages**, **Groups**, **Room rules**, and **Sender rules** to restrict senders, workspace roles, tools, and actions. Room rules use a chat ID or `*`; sender rules use the sender's phone identity. Rules apply together with **Access mode** and workspace permissions. A denial takes precedence. **Inherit** uses broader or default settings; an empty specified allowed list permits no entries.

Groups normally require a mention or reply. To permit unaddressed group messages that pass the other rules, set **Groups → Require mention or reply → Disabled**.

### Answer questions and approvals

For a choice question, react to its message with the displayed number. The reaction flow selects one answer per question and submits after every question has an answer. Type a reply for a custom answer or a question requiring several selections. For a pending approval, react **✅** to approve or **❌** to deny.

These controls belong to the original authorized sender and conversation. Changing workspace access, replacing a question, or reusing a completed control cannot authorize another action.

### Video and voice notes

WebP stickers and MP4 video can be inspected through a sampled first frame. Animation and the rest of the video are not represented by that image. When video audio can be extracted and transcription is configured, Atlas also includes the transcript; it reports when audio is unavailable.

The agent can return saved audio as a voice note or audio file, and saved MP4 as video. WhatsApp voice remains a voice-note exchange; this bridge does not join calls.

## Reply formatting

Agents can still write normal Markdown-style replies, but Atlas simplifies them for WhatsApp.

In practice:

- code fences are flattened to plain text
- headings are converted to normal text
- bold and italics are reduced to WhatsApp-friendly formatting
- long replies are split into smaller chat bubbles

This keeps replies readable in WhatsApp without depending on web-style Markdown rendering.

## Setup

### 1. Enable WhatsApp in Atlas

1. Open **Integrations → WhatsApp** in the Atlas web app
2. Choose which profile should reply
3. Optionally enter your WhatsApp number with country code if you want a pairing code instead of a QR scan
4. Click **Enable WhatsApp**

### 2. Start the bridge

From the repo root:

```bash
bun run dev:whatsapp
```

If the Atlas server is not already running, start it too:

```bash
bun run dev:server
```

### 3. Connect your WhatsApp account

You can link with a phone number or a QR code. This step connects Atlas to WhatsApp. It is not the same as **Access mode**.

**Link with phone number**

1. In **Integrations → WhatsApp**, enter your WhatsApp number with country code (for example `628123456789`)
2. Enable WhatsApp and start the bridge
3. Copy the Linked Devices code when it appears
4. Open WhatsApp on your phone
5. Go to **Settings → Linked Devices**
6. Choose **Link with phone number** and enter the code

**QR code**

1. Start the WhatsApp bridge
2. Wait for the QR code to appear in **Integrations → WhatsApp**
3. Open WhatsApp on your phone
4. Go to **Settings → Linked Devices**
5. Tap **Link a Device** and scan the QR code

After you link, Atlas shows **Connected** only while the WhatsApp socket is live. The badge is not “paired and the worker process is running.” If the socket drops, **Integrations → WhatsApp** shows **Disconnected** even though the worker is still up. That is a down socket, not a ruined session. Wait for automatic reconnect, or restart the WhatsApp worker. Do not use **Reconnect with QR** for that recovery — it deletes the saved session and makes you scan **Linked Devices** again.

Use **Reconnect with QR** only when you intend to replace the linked device: first-time link, a session WhatsApp has logged out or replaced, or damaged saved authentication. Restarting Atlas or PM2 must keep the existing WhatsApp session.

The Linked Devices code (and the QR code) only connect Atlas to your WhatsApp account. They do not control who may chat.

### 4. Choose who can chat

**Access mode** is separate from linking the account.

| Mode | Who Atlas replies to |
|---|---|
| Open | Anyone who messages the linked number |
| Allowed list only | Numbers you add |
| Blocked list filter | Anyone except numbers you block |
| Chat access code | Only chats that send a one-time code |

When access is **Open**, you do not generate or send a chat access code.

When access is **Chat access code**:

1. In **Integrations → WhatsApp**, generate a **Chat access code**
2. Copy the code
3. Open a private chat with the connected WhatsApp account
4. Send the code as a message

Atlas authorizes that chat, clears the code, and blocks chats that do not have access.

## Chat behavior

WhatsApp works in **private chats** and **groups**.

- private chats send each supported message to Atlas
- by default, in a group Atlas responds when someone mentions the connected account, replies to an Atlas message, or sends a supported `/command`
- each private chat and each sender within a group keeps a separate Atlas session
- `/org` in a group changes only that group's workspace selection
- `/profile` changes only that private chat or group's reply profile
- replying to another group message while mentioning Atlas includes that quoted text in the agent turn
- chat access codes work only in private chats
- allowlists and denylists match the sender **phone number**. If WhatsApp identifies the chat as a LID (`…@lid`) instead of `…@s.whatsapp.net`, Atlas resolves the phone from the message (or a saved mapping) before checking the list. The linked owner account is still recognized by its paired LID.

These rules let Atlas participate without interrupting ordinary group conversation. A group sender must still be allowed by the workspace's **Access mode**.

Send `/stop` to cancel the current reply. Send `/pause`, or an addressed request such as “bisa diem dulu ga”, to stop and pause your replies until `/resume` (or “boleh jawab lagi”). In a group this pauses only your conversation with Atlas; other members can still use it. Pauses survive bridge restarts. Requests waiting before you resume are discarded, so send your next request after resuming.

Pairing does not replace workspace permissions. Paired users still follow their workspace role, the profile's assigned tools, and **Channel controls**. Removing a member or changing their role stops their active turns and pending approvals in that workspace. In denylist mode, a blocked phone cannot use a chat access code or bypass the block through its paired account or LID.

**Integrations → WhatsApp → Reply as** sets the default profile. Use `/profile` inside a private chat or group to override that default for that conversation. Starting a new conversation with `/new` preserves the conversation's selected profile while giving it a fresh session.

### Knowledge base answers

Add trusted senders to **Integrations → WhatsApp → Allowed numbers** so they can ask about the replying profile's uploaded references without pairing an Atlas account. Authorized senders on this list can read the profile's ready knowledge base documents when `knowledge_base_search` is assigned and permitted by **Channel controls**. This grants access to all ready uploaded documents available to that profile.

An allowlisted sender without account pairing remains a channel guest. Their other tools stay limited to working with files in **Artifacts**; this does not grant memory, `send_whatsapp`, Bash, or MCP access. Other guests, including unlisted senders admitted by **Open** access, can submit supported work files but cannot search the profile's knowledge base.

When the sender has knowledge base access, Atlas retrieves likely excerpts before answering a factual question. If those excerpts are not enough, the agent searches again with a more focused query instead of falling back to a guess.

Knowledge base, tool, skill, MCP, prompt, and soul changes take effect on the next message while the existing channel conversation and history stay intact.

## Supported message types

WhatsApp can send more than plain text into Atlas.

Supported inputs include:

- text messages
- photos
- voice notes (transcribed, then handled like text)
- supported documents such as `pdf`, `docx`, `xls`, `xlsx`, `csv`, `txt`, and `md`

Attach the original file with **Document**, or use **Photo** for an image. Add the job in the caption, for example “Check these sales figures and return a corrected workbook.” Supported work files include `.xlsx`, `.xls`, `.xlsm`, `.xlsb`, `.csv`, `.pdf`, `.docx`, `.txt`, `.md`, and `.jpg`, `.jpeg`, `.png`, `.webp`, `.gif` images. Pasting a preview is not an attachment.

Atlas saves the original to the replying profile's **Artifacts**, reads it with the matching tool, and creates the requested result there. This works for authorized senders in every access mode; a separate account pairing is not required to save a file. Blocked senders and read-only viewers cannot submit file jobs. Administrators can still restrict tools through **Channel controls**.

Documents can be up to **25 MB** and images up to **5 MB**. Voice notes and audio files up to **25 MB** are saved before their existing transcription flow. An unsupported type, failed download, or failed save gets a rejection instead of an answer guessing at missing content. A scanned PDF may require OCR that the document reader cannot provide; Atlas must report that limitation. Legacy Excel workbooks are read or converted to a new `.xlsx` for editing; macros are not executed or carried into the result. Self-hosted XLS/XLSB conversion requires LibreOffice, which is included in the Atlas container.

In groups, include a mention or reply to Atlas when the mention rule is enabled. If your file lacks a mention, Atlas can offer a reminder you can reply to within **15 minutes** with your request. This uses your original file in the same group and workspace after checking your current access. You can also mention Atlas while quoting the original file. If the reminder asks you to resend, the bridge restarted, or the temporary reference expired, resend the file with a mention. Administrators can permit unaddressed messages in **Channel controls → Groups → Require mention or reply → Disabled**. Continue the file job in the same conversation.

Finished spreadsheets, Word documents, slide decks, summaries, and images return in the chat. Atlas attaches results up to **25 MB**; larger results need an available share link. The text reply stays brief and uses WhatsApp formatting. Send `/attach` or ask “send the file” to retrieve the latest result again.

## Send to a number from this workspace

The WhatsApp account paired in a workspace is the **sender**. A profile that has the `send_whatsapp` tool can message a destination number as that workspace — for example Finance asks “kirim ke Apri 62895… meeting jam 3”.

How it works:

1. Enable WhatsApp for that workspace and scan the QR so the workspace number is connected
2. Start the WhatsApp worker
3. Assign **send_whatsapp** to the profile that should send (new Default Agent profiles get it with the standard toolkit)
4. If **Allowed numbers** is set (or access is allowlist), only those numbers can be contacted
5. Ask the agent to send — it uses the workspace WhatsApp as sender

You can ask Atlas to send the same message to several numbers together, up to 50 per request. Review all recipients and the message in the approval card, then select **Confirm** once. If sending is interrupted, Atlas reports each recipient's outcome. Check any unconfirmed deliveries before retrying to avoid duplicate messages.

The recipient sees a chat from the **workspace number**, not from your personal login. The WhatsApp worker must be running. Meta can restrict unsolicited messages to numbers that have never chatted with that sender.

## Commands

Useful WhatsApp commands:

| Command | What it does |
| --- | --- |
| `/start` | Shows welcome and pairing help |
| `/help` | Shows available WhatsApp commands |
| `/status` | Shows server and model status |
| `/org` | Lists or switches the active organization |
| `/profile` | Lists or switches the profile for this chat |
| `/clear` | Clears the current chat history |
| `/new` | Starts a fresh conversation |
| `/compact` | Compacts the current conversation history |
| `/stop` | Stops an in-progress reply |
| `/pause` | Stops and pauses your replies in this chat |
| `/resume` | Resumes your replies; send a new request afterward |
| `/attach` | Sends the latest file saved in this conversation |

## Troubleshooting

### WhatsApp is enabled but messages do not arrive

Check:

1. the Atlas server is running
2. the WhatsApp bridge is running with `bun run dev:whatsapp`
3. **Integrations → WhatsApp** shows **Connected** (the socket is up). **Disconnected** means wait for reconnect or restart the worker — do not scan a new QR unless you mean to replace the device.
4. Atlas has authorized the chat. If access is **Chat access code** and Atlas asks for a code, generate a chat access code and send it from that chat. **Open** does not use a chat access code.
5. if access is an allowlist, confirm the sender's **phone number** is listed. WhatsApp may deliver the chat as a LID; Atlas still checks the resolved phone, and `/help` from an unmatched chat replies that the chat is not authorized

### Integrations shows Disconnected

**Disconnected** means the socket is down. The saved session is usually still valid. Wait for automatic reconnect, or restart the WhatsApp worker. Do not use **Reconnect with QR** unless you intend to delete the saved session and scan **Linked Devices** again.

Atlas spaces out temporary connection retries, including unknown stream errors reported as **500**. After eight unsuccessful reconnects, it checks again every five minutes. A brief connection does not reset that backoff; five minutes of stable connection does.

Automatic reconnect stops only when WhatsApp has ended the device session: **401** (logged out), **403** (forbidden), **411** (multi-device mismatch), or **440** (device replaced). Then check **Linked Devices** and use **Reconnect with QR**. If Atlas reports damaged saved authentication, restore a trusted backup or reconnect the linked device. Atlas preserves the damaged files instead of silently creating a new identity.

### Connected, but a message is missing

A connected bridge can still fail to decrypt an individual message. Atlas asks WhatsApp to resend it, with a limited retry budget that survives reconnects. Ask the sender to resend the original if it remains unavailable. If several new messages fail, restart the WhatsApp worker or wait for automatic reconnect. Use **Reconnect with QR** only when the device session itself must be replaced.

Keep existing worker logs private: older versions could include linked-device key material. Share redacted error summaries instead of raw logs. If those keys were exposed, unlink the Atlas device in WhatsApp's **Linked Devices** before linking it again.

### A channel worker cannot find the server

Start the Atlas server before starting a channel worker, and check that the configured server address is reachable. A channel worker waits for the existing server; it does not start a second API process. For source installations, run `bun run dev:server` before `bun run dev:whatsapp`.

### Chat access code does not work

Check these first:

1. Confirm that **Integrations → WhatsApp** shows **Connected**
2. Generate a new chat access code
3. Send the current code from the chat you want to authorize

Atlas accepts the current code once. Generate another code if the current one was used or replaced.

### Linked Devices code does not appear

Check these first:

1. Enter a WhatsApp number with country code, then save
2. Confirm the WhatsApp bridge is running
3. Wait a few seconds for the Linked Devices code to appear
4. If it stays empty, use **Reconnect with QR**, then try the phone-number link again

### QR linking is stuck

If QR linking does not finish:

1. use **Reconnect with QR** in **Integrations → WhatsApp**
2. wait for a fresh QR code
3. scan it again from WhatsApp

### Atlas does not reply in a group

Check that the message does one of the following:

1. mentions the connected WhatsApp account
2. replies to a message sent by Atlas
3. sends one of the commands listed above

The sender must also be allowed by **Integrations → WhatsApp → Access mode**. Authorize a number with a chat access code in a private chat before using it in a group. If Atlas should read a message from another participant, reply to that message and mention Atlas.

### The wrong bot is answering

Open **Integrations → WhatsApp** and check the **Reply as** profile. That is the profile the bridge uses for new messages.

### WhatsApp does not use the expected knowledge base

1. Check **Integrations → WhatsApp → Reply as** and confirm it is the same profile you tested in web chat
2. Open that profile's **Knowledge** tab and confirm the document is ready
3. Confirm `knowledge_base_search` is assigned to the profile
4. For a sender without Atlas account pairing, confirm their phone number appears in **Integrations → WhatsApp → Allowed numbers**; **Open** access alone does not grant knowledge base access
5. Check that tool restrictions in **Channel controls** permit `knowledge_base_search`; paired users must also have a workspace role that allows chatting
6. Send the question again; you do not need to use `/new`
