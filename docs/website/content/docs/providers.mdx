## Configure a provider

1. Open **Settings** in the Atlas dashboard
2. Go to **LLM providers**
3. Add a provider and enter credentials if that provider requires them
4. Browse or enter models for that provider
5. Assign a model to each profile that should use it

On first run, Atlas can also prompt for a provider during the setup wizard. See [First-time setup](/first-time-setup).

Settings are saved in `~/.atlas/config.ini` (or under `ATLAS_CONFIG_DIR` when set).

During [First-time setup](/first-time-setup), the wizard uses the same provider form:

## Supported providers

Atlas supports these built-in provider types:

| Provider | Notes |
|---|---|
| OpenAI | GPT and specialist media models, billed with an API key |
| ChatGPT | ChatGPT Plus / Pro through the official Codex runtime. No OpenAI API key. |
| Anthropic | Claude models, billed with an API key |
| Claude | Claude Pro / Max through Claude Code. No Anthropic API key. |
| OpenRouter | Route to many models through one API key |
| Gemini | Google Gemini models |
| DeepSeek | DeepSeek models |
| Cerebras | Cerebras models |
| Cloudflare Workers AI | Cloudflare-hosted models; requires an account ID and API token |
| Fireworks | Fireworks AI models |
| Ollama | Local or Ollama Cloud; multiple instances allowed |
| OpenCode Go | Live catalog from the official OpenCode Go endpoint |
| MiniMax / MiniMax (CN) | Global and mainland China MiniMax endpoints |
| xAI Grok | Grok models from xAI |
| GLM (Z.ai) / GLM (CN) | Global Z.ai and mainland China GLM endpoints |
| Custom (OpenAI-compatible) | Any OpenAI-compatible API; multiple instances allowed |

Most built-in types allow one configured instance each. **Ollama** and **Custom (OpenAI-compatible)** can be added multiple times (for example local Ollama plus a remote compatible endpoint).

For a custom endpoint, pick a preset such as LM Studio, vLLM, LiteLLM, llama.cpp, Groq, Together, or TokenRouter — or enter your own name and base URL — then browse models from that endpoint. API keys are optional for local servers that do not require auth. Choose **Chat completions** or **Responses** in the **API** field to match the endpoint you are connecting. If the provider only documents a `/responses` route, choose **Responses**.

When you change a saved provider's base URL, enter the API key for the new endpoint in the same edit dialog. Atlas never forwards a saved credential to a different URL.

## Connect a ChatGPT or Claude subscription

API keys and subscriptions are different billing paths. Choose **ChatGPT** or **Claude** in the provider list when you want Atlas to use an existing Plus / Pro / Max plan.

The subscription connection belongs to the Atlas host, not one workspace. A **Superadmin** connects or logs out the host account. Workspace admins can add the connected provider to their workspace and choose its available models, but they cannot see the account email or plan. Every workspace that adds the provider uses the same host subscription and its shared limits.

### ChatGPT

Codex is bundled with Atlas. You do not install it separately.

1. As a Superadmin, open **Settings → LLM providers** and choose **ChatGPT**
2. Select **Connect**. Atlas starts Codex ChatGPT login (browser on the host, or a device code you complete elsewhere)
3. Codex reports the ChatGPT account and plan
4. Pick a model Codex lists for that account and save

Codex stores and refreshes the ChatGPT session in an Atlas-owned, isolated credential directory. Atlas does not copy OAuth tokens or load the host user's Codex tools, MCP servers, plugins, or settings. Logging out disconnects ChatGPT for every workspace on that Atlas host without changing a separate Codex CLI login.

ChatGPT requests run as Codex threads. Atlas keeps its own session id and maps it to the Codex thread for resume.

Atlas reads the available ChatGPT models, default model, reasoning levels, and input modalities from the connected Codex runtime. The reasoning menu therefore follows the selected model instead of using a fixed three-level list. Models that advertise image input receive images directly at high detail; other models can use the separately configured **Image parsing** capability. Native ChatGPT image generation uses Codex's automatic canvas and reports the underlying image generator in the result.

The bundled Codex runtime does not currently advertise a stable subscription-backed audio transcription executor, so Atlas does not claim that capability or fall back to an OpenAI API key. Configure **Audio transcription** with a provider that explicitly supports it when you need voice-message transcription.

### Claude

The Claude runtime is bundled with Atlas. You do not install Claude Code separately.

1. As a Superadmin, open **Settings → LLM providers** and choose **Claude**
2. Select **Connect**, then finish `claude auth login` if Atlas asks for it
3. Atlas reuses the authenticated Claude session
4. Pick a supported model and save

Claude Code owns `~/.claude` credentials. Atlas does not read those files or convert the subscription into `ANTHROPIC_API_KEY`. If a Claude API key is present in the environment, Atlas unsets it for this provider so subscription usage is not silently billed as API usage.

Atlas does not fall back from a subscription limit to an API key. If the plan is rate limited or exhausted, that error is shown until the subscription can run again.

Whole-install exports exclude Codex and Claude credential directories. Restoring on the same host preserves its current subscription login; restoring on another host requires a Superadmin to connect again.

TokenRouter and similar gateways only expose the models your key can use, so Atlas tests the connection against a discovered model instead of a generic OpenAI id.

## Connect Cloudflare Workers AI

1. In the Cloudflare dashboard, copy your **Account ID**
2. Create an API token that can run Workers AI
3. In **Settings → LLM providers**, choose **Cloudflare Workers AI**
4. Paste the API token and Account ID, then select a model
5. Use **Test connection** before saving

You can also paste a complete Workers AI API URL in the Account ID field when your deployment uses a custom endpoint.

## Choose a regional provider

MiniMax and GLM offer separate global and mainland China endpoints. Choose the entry that matches the region where your account and API key were created:

| Account region | MiniMax choice | GLM choice |
|---|---|---|
| Global | **MiniMax** | **GLM (Z.ai)** |
| Mainland China | **MiniMax (CN)** | **GLM (CN)** |

After entering the API key, browse the live model list and add the models your account can access. **xAI Grok** uses the same browse-and-add flow without a regional choice.

## Confirm chat capability evidence

When Atlas cannot verify a provider's chat features automatically, a Workspace Admin can record the provider's documented behavior:

1. Go to **Settings → LLM providers**
2. In the provider row, choose **Capability evidence**
3. Set each feature to **Supported**, **Unsupported**, or **Unknown**
4. Select **Save**

Capability evidence is a provider-level override: it applies to every configured model for that provider. Choose **Supported** only after verifying that every configured model supports the feature. **Unsupported** and **Unknown** are both fail-closed, so Atlas blocks requests that need the feature; use **Unknown** when support has not been verified. Use **Provider default** to remove an override and return to Atlas's adapter and model evidence.

Evidence cannot add missing Atlas support. If a feature says its adapter is unavailable, **Supported** is disabled until an adapter implementation is installed.

## Route provider capabilities

Profiles often need more than text chat. **Capability routing** lets a Workspace Admin choose which configured model handles each specialist task without changing code or changing every profile's chat model.

1. Configure the providers and models you want to use under **Settings → LLM providers**
2. Go to **Settings → Capability routing**
3. Under **Image parsing**, **Audio transcription**, or **Image generation**, choose the route you want to configure
4. Choose the **Primary model**
5. Optionally add fallback models in the order Atlas should consider them
6. Select **Save** for that capability

Only models that declare support for the capability and are ready to use in Atlas can be selected. A saved model that is no longer eligible remains visible as **support not verified** until you replace it, so the problem is not hidden. The routing is saved for the active workspace, so another workspace can use different providers and models.

Choose **Disabled** when the workspace should not use a capability. Atlas reports that the capability is unavailable instead of silently sending the request to an unrelated model.

### How ordered fallback works

Atlas checks the primary model first, then each fallback in the displayed order. A fallback is selected only when Atlas can tell **before sending the request** that an earlier target cannot run, for example because it is no longer configured or no longer supports that capability.

Atlas does not silently retry a request on another provider after the request has been sent. This avoids duplicate work or charges and keeps provider errors visible to the operator.

### Check the setup

After saving, test the feature from the same workspace:

| Capability | Quick check |
|---|---|
| Image parsing | Attach an image in chat and ask Atlas what it contains |
| Audio transcription | Send a voice message through a connected channel |
| Image generation | Ask a profile with image generation enabled to create an image |

If **No eligible models** appears, return to **Settings → LLM providers** and confirm that a suitable model is configured and its provider credentials are valid. If a provider rejects a request after it was sent, Atlas shows the error; correct the provider or model settings before trying again.

Other provider-dependent features remain separate from capability routing:

- **Web search** (`web_search` tool) — availability depends on the configured provider and tool assignment
- **Coding agent provider passthrough** — spawn-time credentials for Claude Code / Codex / OpenCode; see [Coding agent](/coding-agent)

## Per-profile models

Each profile selects its own model from the configured providers. Two profiles in the same org can use different providers or models.

Workspace Admins manage provider credentials for their active workspace. Members use models assigned to profiles in that workspace; credentials never cross workspace boundaries.

## Choose a model for one chat

In a web chat, use the model picker beside the message box to override the profile model for that conversation. The choice survives reloads and carries into a branched chat, but does not change the profile or any other conversation. Choose **Profile default** to remove the override.

Atlas only offers models approved in the workspace provider settings. If an admin later removes the selected model, the conversation safely falls back to the profile model. Only the conversation owner or a Workspace Admin can change an existing conversation's model.
